# 架构审查评估与 M0 更新计划

日期：2026-10-19。核查基线：`e628f5e`、PRD V0.6、ADR-0001 和本机已有 macOS arm64 开发应用目录。

状态：采纳下述工程方向及验证顺序；接口为待 spike 验证的设计草案，尚未实施或冻结。本次只更新计划与交接文档，不修改业务实现、PRD 原件或原型，不代表 M0 完成。本文工程优先级与 PRD 的产品 P0/P1/P2 分开理解。

## 1. 结论与采纳范围

八项建议均有应采纳的内容，但需修正三处判断：当前单请求 health 不能证明业务性能不合格；本机打包态 CSP 失效未复现；不可变历史运行不能归入可清理的派生缓存。

先做存储与失效 spike，同时设计任务/协议契约；随后验证常驻引擎和真实候选库打包。CSP 显式交付及打包回归作为独立小项优先处理。模型网关在 M0 形成 ADR，在任何真实模型调用前通过授权与凭据验证。渲染端先约定数据语义，再按首个真实模块需要选库。

## 2. 三个 spike / ADR 的交付定义

以下 ADR 编号为预留，只有通过相应验证后才改为“采用”。测试替身仅用于基础设施故障测试，不得宣称为业务能力。

### S1 / ADR-0002：源真相、场景、历史与失效

**目标：** 避免关系库与可变三元组库双写成为两个真相来源。优先验证 SQLite 保存版本化规范数据及元数据、RDFLib 从不可变输入快照构建计算图的路线；不据此提前冻结文件格式或宣称图性能足够。

数据责任按下表划分，仍在产品层保留 FR-006 的五层展示边界。

| 存储责任             | 内容                                                                                                  | 写入、清理与恢复规则                                                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 项目源真相           | 本体、断言事实、映射与行来源/所有权、查询/约束/规则/行为/场景定义、必要配置和版本、ChangeSet/撤销依据 | 单一事务化提交边界；提交时再次校验基准版本；快照及迁移必须可恢复。不能用丢失这些内容的“缓存重算”恢复项目。                                    |
| 隔离场景状态         | 从显式基准创建的场景副本、当前工作轮次及已提交轮次引用                                                | 与正式项目断言隔离；单轮成功才提交。取消回滚未提交轮次，不伪装已提交轮次从未发生。                                                            |
| 不可变历史与持久证据 | 历史运行输入、配置、逐轮状态、结果、日志、必要的 job/提交记录、用户保存的报告及快照引用               | 不被重算或缓存清理覆盖/删除。运行按 FR-705 可由用户明确删除并展示影响；引用中的快照不能被提前回收。内容缺失时不得承诺可重放。                 |
| 可重建派生视图       | 当前推导、查询/SHACL 的计算结果载荷及索引                                                             | 输入和定义版本绑定；过期保留原因与重跑入口。只有未被历史/报告固定引用且可安全重建的载荷可回收；已保存的结果定义、状态和来源引用不能随之丢失。 |

版本至少区分三类，不用一个递增计数承担所有职责：

- `projectRevision`：正式提交与 ChangeSet 乐观并发控制。
- `inputSnapshotId + dependencyVector`：运行依据及相关本体、事实、规则、约束、查询、行为、场景参数等版本。只纳入本次能力实际依赖，按附录 D 判定过期；仅改模型配置不使确定性领域结果失效。
- `executionSemanticsVersion + engineVersion + dependencyLockHash`：计算语义和引擎/依赖实现来源。缓存键建议包含项目、数据范围、相关输入摘要、定义摘要、计算语义及实现版本；保存快照来源。引擎或依赖升级默认隔离缓存，只有通过等价性测试并记录明确的缓存兼容版本才允许复用。复用仍须校验依赖，不能只靠 TTL，也不能把无关项目元数据变化全部视为领域失效。

必须在一次提交边界内完成正式数据变化、版本推进、来源所有权更新、依赖失效标记，以及关联 `operationId / jobId` 的持久提交标记。提交标记与正式数据同一事务持久化，不能留下“数据已提交但无记录可核验”的窗口；job 终态允许据此恢复对账。计算得到的旧快照结果可保留为历史，但发布为“当前”前必须重验依赖；旧任务迟到不能覆盖新版本。禁止在两个存储之间先后修改可变真相后靠补偿拼一致性。

**交付：** ADR-0002、存储接口及最小格式/迁移草案、依赖键与附录 D 对照表、版本化的机器可读失效规则与 `staleReason` 码表、代表样例、故障注入脚本及原始结果。码表在 S1 设计评审后作为引擎、U1 和 Agent 的共同契约来源，展示文案另行映射，不在各层重复发明规则。

附录 D.2 的九行都须有可执行的正/反例映射；前八类仅对实际依赖的结果产生过期原因，并允许一项结果记录多个原因及对应依赖版本。“仅模型服务或 Agent 提示配置变化”是**不使确定性领域结果失效**的反例规则，不得为了凑九个枚举而生成 `staleReason`。历史身份、执行失败与取消也不混入过期原因；引擎/依赖升级的缓存隔离单列实现兼容规则。

S1 同时交付至少两档合成规模（例如 G-base 的 1× / 10×，100× 按资源余量选做），分别记录快照加载、RDFLib 建图及固定只读查询的耗时与内存原始值。生成器需保持结构、使用独立对象 ID/命名空间（不能以同 ID 重复 G-base 冒充扩容），并记录稳定随机种子、实际三元组数、输入/查询摘要，记录设备、库版本、冷/热条件、重复次数和测量方法，与 B1 使用相同口径。此时不设业务容量通过线；超时、内存不足或中止同样记录，出现路线风险须在 S2 冻结前复评，不以“只记录”掩盖失败。Q5 未确认前不能据此宣称容量达标。

**退出门槛：**

1. 映射替换和 ChangeSet 在提交前/中/后模拟取消、异常、磁盘写失败及进程退出；恢复只见最后已提交状态，旧 ChangeSet 拒绝提交，来源与所有权同步恢复。
2. 删除源行不删除手工事实；人工修改、受管范围和多来源所有权冲突均可定位并阻止不合法提交。
3. 规则撤回只替换当前推导；附录 D 每类变化得到准确的过期原因；缓存清理不损坏历史、保存的定义和正式数据；仅改模型配置不错误失效领域结果。
4. 场景副本隔离；固定轮次提交/取消边界符合 E.2；历史输入、结果和已提交轮次不被新运行改写。
5. 两档规模测量和附录 D 正/反例映射均有原始记录；机器可读规则与文档对照无遗漏，不把合成负载当作完整业务基线。
6. 对本 spike 覆盖的 G-base、G-map-empty、G-behavior 和 E.5 项目逐项记录实测范围与完整预期集合/顺序。未执行的业务用例保留未通过，不以存储模拟替代完整 M0 基线；迁移失败可恢复，重放输入缺失时如实标识。

### S2 / ADR-0003：常驻协调器、v2 协议与 ExecutionJob

**目标：** 一次启动建立一个受主进程监督的本地引擎会话，复用 stdio；耗时计算不得阻塞取消、心跳或协议读取。M0 正式领域能力仍可只有 health，但生命周期和任务骨架必须有可执行验证。

建议进程责任：Electron 主进程负责可信来源、限权调度和引擎监督；Python 常驻协调器负责协议与有界队列；耗时库计算使用可协作取消或可终止的隔离执行单元。具体 worker 方式由 spike 决定，不因“常驻”默认无限并发或多个任务共享可变图。

#### v2 契约草案

统一用 `kind` 区分三类信封；以下只是形状说明，正式 schema 还需定义各方法字段、范围和字节限额。

```json
{"kind":"request","id":"r1","protocolVersion":2,"method":"health","params":{}}
{"kind":"response","id":"r1","protocolVersion":2,"ok":true,"result":{"status":"ok"}}
{"kind":"response","id":"r2","protocolVersion":2,"ok":false,"error":{"code":"METHOD_NOT_ALLOWED","messageKey":"engine.methodNotAllowed","params":{"method":"unknown"},"retryable":false}}
{"kind":"notification","protocolVersion":2,"engineSessionId":"s1","projectId":"p1","jobId":"j1","seq":3,"event":"job.progress","data":{"stage":"reasoning","completed":5,"total":10}}
```

- 启动先执行稳定 bootstrap `hello`，提交双方支持的协议版本，返回选定版本、引擎版本、会话 ID、实际能力与 limits。无交集则结构化失败，不隐式降级。未完成握手不接业务请求；只有已实现且验证的能力可以声明。
- v1 health 是开发骨架，无外部兼容承诺；v2 改造双端同步交付，旧客户端/引擎组合明确报不兼容，不长期维护两套业务协议。
- request、response、notification 和每个方法的 `params` 均严格校验。响应必须满足成功只有 `result`、失败只有 `error`，校验完整外层而不只校验 health 载荷。
- 一行一个 UTF-8 JSON；支持 chunk 拆分、多行粘连及跨 chunk 字符；输出带换行并及时 flush。限制单帧和未完成帧缓冲，stdout 仅协议，stderr 为限量脱敏诊断。
- `pendingRequests: Map<requestId, ...>` 替代单一全局请求槽，按会话和 ID 关联。重启后旧会话响应、重复/未知响应及非法状态事件不得结算新请求或污染其他项目。
- `jobId` 采用跨项目、跨引擎重启唯一的不透明标识，持久保存且不复用；项目任务通知显式携带 `projectId`，路由同时校验项目、job 归属、会话和序号，不能只靠全局唯一 ID 越过权限检查。非项目级会话事件使用单独 schema，不伪造项目 ID。
- 长任务创建请求快速返回 `jobId`；通过限权订阅获取进度，通过 `job.get` 重建状态。`job.cancel` 是携带 `jobId` 的请求并有确认响应；“已受理取消”不等于“已取消”。不能用杀死整个协调器取消单个 job。
- 启动/握手超时、单请求响应超时、任务总时限、心跳超时、取消收尾期限、每帧/队列/分页/内存限制分别配置，按能力有界调整。心跳不能无限延长总时限；5 秒可保留为短探针策略，不作为所有任务总时限。
- 大结果返回不可变 `resultId`，再以有稳定顺序的游标分页；游标绑定项目、结果版本和范围，拒绝失配。流式只在分页不足时再引入，避免任务完成通知携带全部结果。

#### ExecutionJob 草案

```text
queued → running → succeeded / failed
queued → cancelled
running → cancelling → cancelled / failed / succeeded
```

`cancelling → succeeded` 仅用于整个任务已成功完成并持久化最终提交/终态后才到达取消请求的竞态，必须显示任务已完成；沙盘此前仅有若干轮提交，不构成整个任务成功，取消当前未提交轮次后仍为 `cancelled`，保留已提交轮次。禁止为了满足取消按钮而隐藏已提交数据。进程崩溃后先核对持久记录与最后提交点，未能完成的任务标记失败及原因，不能直接认定成功或已取消。

任务记录至少包含 `jobId / projectId / capability / inputSnapshotId / dependencyVector / executionSemanticsVersion / engineVersion / dependencyLockHash / state / stateVersion / limits / resultRef | error / timestamps`；持久 run 记录同样保留引擎与依赖实现来源。传输会话 ID 和事件序号独立记录，重连可获取权威状态。M0 冻结谁拥有持久 job 状态与提交记录，避免主进程与引擎各自判定终态。

对有逐轮提交语义的沙盘 job，增加 `committedProgress`：至少含 `runId`、`lastCommittedRound` 和 `snapshotRef`；无已提交轮次时显式为 `null`。非逐轮任务按能力 schema 区分“不适用”，不伪造轮次。引用依据 S1 同事务的运行/提交记录恢复，不另造独立可变计数；轮次与快照必须匹配同一项目和运行。任务 `cancelled` 或 `failed` 时仍可带该字段，`job.get` 与历史运行可查最后已提交点；UI 同时显示收尾状态和已提交轮次，不将其显示为成功的当前结果，也不自动续跑。验收区分取消前零提交、已有若干轮提交、提交成功但响应丢失、最后成功提交后才取消四类情形。

按项目串行正式写入，只读任务绑定不可变快照；队列和全局并发有明确上限。取消后的处理遵循操作语义：查询不写项目；映射/ChangeSet 不提交半批；沙盘保留已提交轮次。协调器退出拒绝所有相关待响应请求，有限退避重启；不自动重放写入或静默续跑沙盘。若提交成功但响应丢失，以提交记录恢复状态，不能盲目重试。

注册表以能力 ID 关联参数/结果 schema、数据范围、read/write 分类、ChangeSet/授权要求、limits、取消边界和实际实现状态。UI 与 Agent 复用同一应用服务及确定性引擎适配器；UI 仍只暴露业务命名 bridge，Agent 只获得筛选后的白名单。不得生成任意 `invoke(method, params)` 或使 Agent 自动确认自己的修改。凭据、网关等主进程能力不能为了“统一”被强塞入 Python。

契约先采用一套版本化 schema、错误码清单与双端共用成功/失败样例；生成类型或校验器可随后引入。区分传输错误与任务失败，bridge 保留 `code / messageKey / params / retryable / 安全详情`，UI 映射 PRD 8.6 四段式解释。取消、过期、不支持与失败分别呈现，禁止向 UI 或外发载荷回传原始业务异常、密钥和堆栈。

错误的可选 `params` 按错误码/messageKey 定义白名单、类型、条数及字节上限，承载工作表标识、行列位置和字段等安全定位参数；双端共同拒绝未知或越界参数。明细过多使用受限引用/分页，不能在错误信封内塞入全部数据。参数不得包含单元格原值、完整路径、凭据或堆栈；FR-303 的动态定位和 PRD 8.6 的四段式说明在 UI 组装，错误参数也不自动获得模型外发授权。

**交付：** ADR-0003、v2 schema/错误码/公共样例、状态转移表、单一能力注册表草案、health 常驻端到端验证、测试专用任务的排队/取消/崩溃报告。业务未实现的能力不进入正式能力声明。

**实施前设计评审门：** v2 schema、错误参数、ID 唯一性与通知路由、状态转移和已提交进度须经独立审查；逐项映射 S1 的取消、崩溃对账、提交标记恢复及迟到结果故障用例，保存差异与评审结论。设计可与 S1 并行，但相关存储接口未明确、关键问题未关闭前不冻结契约或进入 S2 实施。设计评审通过不等于 ADR 已采用。

**退出门槛：**

1. 同会话多次 health 复用进程；并发/乱序响应正确关联；拆包、粘包、UTF-8 分片、超长未终止帧、坏 JSON、重复 ID、未知方法、版本不兼容均有跨端测试。帧缓冲在追加前按字节限额检查，含多字节字符、连续超限 chunk 与终态后到达 chunk；达到限额后停止累积并清理 pending。同步修正当前 health 适配器中“持久任务在 M1 再设计”的旧注释。
2. 忙碌计算时仍能接收取消/心跳；无总量的计算显示阶段而不编造百分比；满队列拒绝有结构化错误，不能无限排队。
3. 取消与完成竞态终态不倒退；隔离 worker 异常不误终止别的任务；引擎崩溃时 pending 清理、状态恢复和退避有测试。持久原子语义依赖 S1 的提交接口验证。
4. requestId/jobId/项目/会话不串线；页面刷新或重建可查询任务状态。renderer 崩溃/无响应时保留已提交数据并按规则恢复，不能自动再发写入。
5. TS/Python 对同一公共样例接受/拒绝一致，含 `projectId` 不匹配、非法错误参数、取消但保留已提交轮次及零提交反例；错误码与安全参数完整穿过 Python → 主进程 → bridge → UI，UI 按错误类型提供可操作说明。

### S3 / ADR-0004：模型网关与进程归属

**目标：** 任何模型请求只有一个最终发送入口，确定性 Python 引擎不持有模型凭据或直接调用模型。

主进程拥有凭据适配器、版本化授权、最终载荷检查、实际发送与最小记录。Agent 编排初期可在主进程异步服务运行；若阻塞或隔离需要，放 worker/utility process，通过窄接口申请调用网关，不获得绕过网关的凭据和模型发送路径。选型验证不能把“采用异步”直接当成“不阻塞”的证据。

授权绑定项目、范围、用途、规范化实际接收端点、凭据主体/不透明配置版本。每轮包含工具结果、摘要、历史、错误的最终请求都重新检查；重试也须检查当时的授权和配置。Base URL、凭据主体或新配置身份变化立即导致旧授权失效，显示名称变化不扩大失效。跨端点重定向不能绕过接收端授权；配置在检查与发送间变化时停止发送并重新检查。切完全本地阻止新请求，已发送数据无法撤回的提示遵循 FR-902。

优先评估 Electron `safeStorage` 作为主进程凭据加密适配器，但它提供 OS 支持的本地加密，不等于各平台同等强度的独立凭据库。密文存放应用私有设置，不能进入项目、导出、会话或普通日志；加密不可用时禁止静默退化持久明文。目标平台需验证密钥库锁定/不可用、签名升级及恢复失败；Linux 若采用提供 `basic_text` 的后端需明确拒绝不安全持久化。API 以仓库锁定 Electron 版本验证，不直接照搬最新文档中的新接口。

业务 renderer 不接收解密后的凭据；设置页若用于首次录入 API Key，只允许短暂提交到窄接口，不回显已存密钥，不写普通 client store。是否使用独立设置窗口在 ADR 中记录，不作“renderer 在录入时绝不接触任何字符”的不真实承诺。

最小日志仅记录目标服务、用途、范围、授权结果与时间等元数据，不保存业务正文、完整工具结果或凭据。注册表中的读权限和模型外发权限分别检查。

**交付：** ADR-0004、进程/调用路径、授权绑定和失效表、凭据接口、假接收端测试与日志检查结果。本轮不配置真实模型或外发业务数据；Q9 受测协议/服务仍待确定。

**退出门槛：** 使用合成数据与本地假接收端，证明无授权/超范围/端点或凭据版本变化/完全本地/恶意工具输出/重定向均无法绕过检查；同一未变化范围可复用授权；模型失败不影响本地保存；敏感明文不进入项目、导出、日志。真实模型协议、结构化输出与工具调用须在 Q9 明确后单独实测。

## 3. 独立工程项

### C1：显式 CSP 与窗口生命周期

生产 HTML 在资源加载前提供 meta CSP，开发继续支持 nonce 和 HMR。策略从同一配置来源生成开发与生产变体。C1 评估生产“仅 meta（移除 header 注入）”和“meta + header”后选择一种交付方式，记录锁定版本、交付差异与理由，对选定方案执行阻断/正常功能矩阵；存在未决兼容性时再做最小对照探测，不要求为比较而长期维护两套实现。若选择并存，两个交付路径也从该配置生成且验证最终叠加效果，不维护第三套手写策略。开发/生产仍可按 HMR 需要有明确变体，不把合理的环境差异误判为三份策略来源。不得向开发页面直接注入会阻断 Refresh/HMR 的生产 meta。

保持生产脚本不允许 `unsafe-inline`/`unsafe-eval`；样式优先使用本地 CSS。引入 UI 库时分别验证 `<style>` 注入、style 属性、CSSOM 路径，不能把 React `style={{}}` 统一当成会被阻断。本机实测 CSSOM 属性赋值生效，style 元素和 `setAttribute('style', ...)` 被拦；当前源码没有 React 内联 style 的已发生兼容缺陷。

同时将窗口创建的安全设置集中到 `web-contents-created` 等统一入口，保留来源/主 frame 校验；定义 `render-process-gone` 与 `unresponsive` 的提示、重建和任务重连策略。自动恢复不得丢失已提交项目状态或自动重复写任务。

验收同时覆盖开发 HMR、构建态和真实打包 executable：内联脚本、未授权资源、外联连接与 frame 被有效拦截，正常 UI/CSS、health、导航和隔离配置可用。只检查 meta 存在或控制台没有报错不能视为通过；本次已做的较窄探测范围见独立记录。

### B1：真实候选引擎库打包

在隔离分支/验证环境固定 RDFLib、pySHACL 及实际规则实现候选的完整依赖，先运行最小真实 Turtle 解析、只读查询、RDFS/受控规则和 SHACL 检查，再执行 `package:dir` 并从产物内运行相同样例。引入依赖即启动验证，不必等到 Q6 最终冻结，更不能等 M2。

检查 PyInstaller 隐式导入、资源/插件、动态库与许可证清单；实测 `SERVICE`、远程 `FROM`、解析器/验证器可能产生的隐式外联均被拒绝，不能用“配置关闭”替代证据。候选组合只承诺附录 C 的有限语义，不能以库默认推理模式扩大为完整标准能力。

记录包体、冷启动/热调用耗时、内存峰值、样例规模、设备、版本和原始测量值；业务容量是否达标须等待 Q5 的目标，不能先编造秒数或性能提升。首轮可在现有 macOS arm64 开发环境证明依赖可打包；Q2 确定的首发平台仍需干净设备、无系统 Python、断网、签名安装等后续证据。当前空引擎打包通过不覆盖这些事项。

### U1：渲染端缓存与草稿边界

UI 读取的项目/任务/结果状态以主进程应用服务与引擎的权威记录为准；编辑草稿、选中项和展开状态保存在 client store。六模块共用项目服务和结果身份，不各自缓存一个可变项目副本。

查询 key 至少区分项目、结果/快照、范围、参数和实际依赖；结果过期原因、任务终态和历史标识显式呈现。切项目、提交新版本后丢弃旧订阅的迟到更新；未提交草稿不能被自动刷新覆盖。默认分页/限量，后台结果不会因页面卸载就被误报取消。库选型随 M1 首个真实读写流程确定，并用该流程验证。
