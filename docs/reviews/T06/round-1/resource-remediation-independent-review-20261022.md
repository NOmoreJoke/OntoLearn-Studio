## P2-1：接受内部优化，保持完整可观察语义

### 编辑索引与增量 effect

建议最小内部结构为对象 ID 集合、通知 ID 集合、以 `_json(fact)` 为键的事实字典及 `(subject, property)` 到事实键集合的槽索引。通知列表仍保持动作顺序。单值 set 仅替换该槽，多值 add 仅插入尚不存在的规范化事实。输出/明确状态边界才按现有 `_normalize` 规则物化排序列表。

必须保留以下约束：

1. **先验证再索引化。**原始状态中的重复事实、重复对象、单值矛盾不能被字典/set 静默去重后变为合法输入；`_state` 原有错误类别与顺序保留。无效对象/属性、基数不匹配即使“看起来无变化”仍须拒绝。
2. 值与事实键继续使用 typed `_json`，不用 Python `==`/原生数值集合替代；否则 `false`/`0`、`1`/`1.0` 的原比较语义可能变化。
3. create 先查对象及通知身份碰撞，有序处理全部 initial；新对象和 initial 保持一个源动作、一个轨迹。event-only declare、删除对象及其关系入边的事件编辑不能因共用索引而改变既有行为。
4. 每实例验证 scratch 从相同 after_events 开始；可引用本实例此前 create，不能因共享可变索引看到 peer create；冻结条件也不能引用正在变化的候选索引。
5. set/add 的 `effect` 比较动作前后受影响槽的**规范化事实集合**；有效 create 必有对象新增，notify 必有记录新增。不能用“执行过删除/插入”当 changed：同值 set 会先删后加但原 effect 是 unchanged。也不能因为推迟排序就把内部字典插入顺序当成状态差异。
6. 任一失败仍只返回原类错误和既有完整/前缀证据；局部修改只能留在私有废弃副本，无 candidate/新 consumption，`executed_actions=[]`。候选模拟已成功前缀仍是 discarded，不能因索引重构改变其语义。

首个新候选可以保留当前 per-instance scratch 复制，先消除已证实的重复扫描；copy-on-write overlay 更复杂，若加入需单独核对隔离和失败前缀，不宜为追求推测收益一并扩大重构。

### 分桶冲突：可保留原 combinations 首个冲突

原实现从全局 write 序号按 `(i,j)` 字典序返回第一对冲突。只“按槽分桶并返回第一个冲突桶”会改变完整 conflict/evidence，不能视为等价。

总控拟案可成立，具体前提及简化实现如下：

1. 仍按原 intents 顺序、同一 create 的 initial 顺序展开全部单值写，并赋全局序号。每写预计算槽、实例 `(event_id, behavior_id)`、typed `_json(value)`；保留原 write 与完整 intent。
2. 每槽仅将相同 `(instance,value)` 的重复项压缩为**最早原 write**。这是查冲突用的临时索引；完整 intents/action_trace、源动作计数和所有其他动作不压缩。
3. 桶内按原序排列 unique 项。单实例或单值的桶无冲突，可跳过。其余桶先扫描与第一项 u 相冲突的最早 j；若存在，这是该桶的第一对冲突。
4. 若 u 没有冲突，则除 u 外每项必属于“同实例、不同值”或“不同实例、同值”之一；不可能同时与 u 在实例和值上都相同，因为已去重。非单实例且非单值保证两类都有；因此第二个 unique 项一定与另一类中的某项冲突。扫描它对应的首个 j 即可。这一条件下，不必泛化为桶内全对比较。
5. 对所有有冲突的桶候选按原 `(i,j)` 取全局最小，再用这两项原 intent 生成与旧实现相同的 conflict、slot 和完整 evidence。

证明中“若无冲突”必须指“第一项没有可冲突的后继”，而非“第一、第二项这对无冲突”。不去重而直接检查原第二项也不成立：`[(A,x),(A,x),(A,y),(B,x)]` 的前两项都是重复代表，真正第一冲突是原索引 `(2,3)`。压缩只保留最早同对后，第二 unique 为 `(A,y)`，才适用上述证明。

两个防退化反例：

- 同槽 `[(A,x),(A,y),(B,y)]`：必须报 `(0,2)`，不能每实例只保最终值 y 后漏冲突。
- X 槽在原序号 `(0,9)` 冲突，Y 槽在 `(1,2)` 冲突：原实现先报 X 的 `(0,9)`。按较早“闭合”冲突或桶遍历顺序返回 Y 会改变证据。

这项算法静态上避免了无关槽和同值/同实例的大量全对比较；**本报告没有实测性能提升，也没有给出倍数或时延承诺。**

## P2-2：完整输出的成本与仍缺的决定

**严重度与证据。**保留资源风险待处置，不将其直接判为已违反明确容量验收线。planner.py:698–751 对排序后的每行为和每 accepted event 产生独立 decision。无触发时仍有 `event_mismatch`/`disabled` 理由、版本与空 conditions，符合 interface.md:11、24、32 的完整集合约定。原报告建议“不匹配时只留 reason、不保留完整 condition 结构”，实际上当前已不评估这些条件，conditions 已是空列表；再删字段就改变 schema。

**合法反例。**1000 行为×1000 不匹配事件应有 100 万条决定、零动作；不能因为零动作就略掉决定，也不能只返回1000条后说“完整”。该材料化返回值本身需要 Ω(BE) 的记录空间。若要求每条 decision/conditions 保持当前独立可变对象，不能靠所有 mismatch 共用一个 dict 或空 list 降低内存；修改一条不得污染其他条。

**原测量的地位。**MiniMax 报告记载 1000×1000 峰值约346MB、10.7s，属于原外审合成输入测量，未在本任务重跑。PRD 没有规定“1000行为×1000事件”容量目标、该设备、346MB上限或10.7s阻断线，也未规定行为/事件/初始字段数上限。该结果能支撑资源风险和正式接线前的工程决策，不能单凭这些数值宣称已违反 PRD 具体阈值；同样不能因为没有阈值就宣称适合生产规模。Q5 本应形成可测指标，其关闭状态须由总控核验，不能由本 agent 代填。

**可保当前语义的最小内存改进：**

- `PreparedRound.document/binding/reasoning_input`（243–258）当前会多次解析整个序列化文档。单次 plan 可在已有脱离输入的 doc 上计算一次相同 binding/digest 并复用，避免额外的临时整文档副本；不缓存或对外暴露可变内部权威。

## 4 项 P3 的逐项契约核对

### P3-1：有序 initial 单值覆盖

位置：planner.py:167–179、192–203；interface.md:7、22；t09-adaptation.md:7。同一个 create 内 `status=FIRST` 后 `status=SECOND` 的最终状态为 SECOND，完整 action_trace 中 initial 原列表仍保留 FIRST、SECOND，effect=changed 表示**整个创建动作**改变状态，并未声称每个字段各生效为最终事实。

原报告称“没有任何输出提示 FIRST 被丢弃”过强：它自己给出的完整 trace 正保留两项。多值 Equipment/HighRiskEquipment 是不同值可共存，不是“相同值重复未去重”的证据。PRD E.1 没有规定同一 create 的 initial 必须预检异值报错；有序列表、单值覆盖和既有实现可形成一致合同。

建议文档明确“initial 按列表顺序应用；单值同槽后项覆盖，轨迹保留全部项，任一初始单值写均参加跨实例竞争”。不自动采纳 `cardinality_violation` 新拒绝规则。反例：原合法 create FIRST→SECOND 会被新预检拒绝，即改变兼容行为。无 peer 时可覆盖；若 peer 写 SECOND，FIRST 仍必须触发竞争，不能只看最终 SECOND。

### P3-2：create 与属性幂等不是同一操作

位置：planner.py:186–190、204–215、849–852；t09-adaptation.md:9。两个实例都创建 SHARED，第二次对象分配碰撞拒绝，符合“原 create 碰撞仍拒绝”。E.1 的同值**属性写**“可幂等去重”不等于要求对象创建合并；“可”也不是所有动作自动幂等的授权。事件的 declare 是明确独立的幂等节点登记，行为不允许 declare。

建议在 interface.md 直接引用这条例外以减少误解，保留现行为。改 create 为幂等可能把两个独立创建意图合并，改变对象生命周期/通知结果及失败阶段，不能作为本轮资源修复。重复事件本身已有消费去重，与新事件再创建同一常量 ID 的碰撞是两个问题。

### P3-3：成功事件位置是可选新增诊断

位置：planner.py:329–388、861–867；interface.md:30、52。成功 event_trace 只有 ID/理由、无法独立区分完全相同 ID 重投的源数组位置，这个观察正确；但当前明确承诺的是**错误**的源位置。PreparedRound.document.request.events 保留原数组，输入快照保存归正式轮次 owner，本私有 plan 并未承诺单独覆盖全部重放材料。

如未来要让成功轨迹直接定位每次投递，可批准为 event_trace 增加 source index/sequence，另加精确重投回归。这不是现存失败位置缺陷的回归，不应改称当前合同违约。

不采纳直接向 consumption.events 增加 event_index：现校验严格只接受 event_id/fingerprint，新字段会被 `_shape` 拒绝；同 ID 同内容改投递位置/sequence 仍必须 no-op，消费身份不应依赖本次投递位置。反例：事件首次位于数组下标0，续轮重投位于下标5，不得视为新消费；老账本也不能因新增必填位置失效。即使将其定义为纯诊断元数据，也需要显式版本与兼容策略，不是免费字段。

### P3-4：明确完整 Diff，不从冻结集反推行为删除
