## 二、七项高优先级问题

### R01｜记录版本，还不足以防止旧结果被当成当前结果

**位置：** [FR-304，L364](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:364)、[FR-501，L410](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:410)、[FR-703，L482](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:482)、[可靠性，L709](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:709)。

**已有要求：** 映射、运行、规则和行为关联版本；沙盘隔离执行。

**缺口与影响：** 未说明事实数据、推导结果、测试数据各自的边界，也未规定修改上游后哪些结果过期。例如删除告警后，旧的“高风险设备”推导、查询缓存、行为测试和报告可能继续显示。即便每条结果都带版本，用户仍可能误以为它反映当前项目。

**建议补充：**

- 在产品层区分本体定义、事实数据、推导结果、场景副本；不必在 PRD 指定底层存储实现。
- 查询明确采用“事实”还是“事实＋某次推导结果”；SHACL 明确验证哪个数据范围、是否包含推导结果。
- 修改本体、数据、映射、约束、规则或行为后，受影响结果标为“已过期”，说明原因，并提供重跑入口。
- 历史运行仍可查看；将其用于当前结论、下一步执行或报告时，必须明确所用快照，避免悄悄混用新旧状态。
- 重算应替换对应的旧推导结果；撤回不再成立的推导，不应误删用户录入的事实。

**验收示例：** 删除一条用于推导风险等级的告警后，原推理结果立即标记过期；若该告警是某项风险结论的唯一支持依据，重跑后撤回该结论；仍有其他有效依据的结论应保留。新的查询和报告与新版本一致，旧运行仍可追溯。

**标准依据：** SHACL 是否采用推导后的数据是需要明确的执行选择，标准并不要求所有实现自动执行完整 RDFS 推理。[W3C SHACL：Relationship between SHACL and RDFS inferencing](https://www.w3.org/TR/shacl/#shacl-rdfs)

### R02｜“重跑不重复”没有解决身份冲突、旧数据撤回和人工修改保留

**位置：** [FR-301—304，L346](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:346)。

**已有要求：** 唯一标识规则、映射版本、影响预览，以及避免无提示地生成重复个体或关系。

**缺口与影响：** 没有定义同一文件再次导入是追加、更新还是替换；源表删行、改主键、多个工作表引用同一设备，以及导入后人工修正字段时，处理结果不确定。仅防重复无法保证数据正确。

**建议补充：**

- 明确实体身份规则：数据源命名空间、业务主键、复合键、空主键、重复主键、编码规则和跨表引用。
- 明确 P0 支持的重跑方式。可先只支持“替换该映射上次生成的数据”，将多种合并策略留待后续；这属于建议，需由产品确认。
- 保存生成数据与源表行、映射版本之间的来源关系，支持预览新增、修改、删除和冲突。
- 明确源数据撤回、多个来源共同支持同一事实、人工改动和导入改动冲突时的处理方式。
- 定义空值、字符串编号前导零、日期等常见值的转换规则，以及错误时整批失败还是允许明确选定的部分导入。

**验收示例：** 同一文件重复执行不增加实体；某设备编号为字符串 `001` 时保持身份稳定；删除源行后按选定策略撤回对应来源的数据；映射重跑不静默覆盖人工修正；失败不留下不明状态的半批数据。

### R03｜SHACL 和自定义规则列为 P0，但用户无法据此知道如何创建和修复它们

**位置：** [范围总表，L174](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:174)、[FR-500—504，L397](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:397)、[数据对象，L659](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:659)。

**缺口与影响：** 当前写了运行检查、展示推导、定位约束与规则，却没有约束和规则的创建、编辑、启停、版本管理及测试流程。内置案例可以预置内容，但新建空白项目和企业 POC 会缺少关键操作。

**建议补充：**

- 给出最小约束模板，例如必填、类型、取值范围、数量约束；明确首版具体支持哪些。
- 给出最小规则编辑方式，例如“满足哪些条件，推导哪个事实”，并提供输入样本、预期输出、实际输出和错误定位。
- 明确哪些内容允许表单编辑，哪些只读或需要专业编辑；将推理规则与会改变场景状态的行为动作分开解释。
- 如果首版仅允许预置规则或模板参数修改，应同步收窄“自定义基础规则”的范围表述。

**验收示例：** 在空白项目中，不配置模型也能添加一条受支持约束和规则，构造不合格样本，看到对应错误，修复后通过，并查看一条真实推导依据。

### R04｜沙盘写了“确定性”，但还没有定义决定结果的业务规则

**位置：** [内置案例，L147](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:147)、[FR-600—604，L428](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:428)、[FR-700—704，L462](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:462)。

**已有要求：** 明确输入、规则、事件、资源、运行记录和隔离；Q7 也已承认推演类型待确认。

**新增缺口与影响：** 即便选择固定轮次，仍不清楚每轮先产生告警还是先处理工单、人员如何消耗产能、同一事件是否重复建单、行为冲突如何排序、何时停止。案例只有“创建工单”，尚未给出“分配、处理、完成”的最小规则，因此人员数量怎样影响积压缺乏依据。相同输入可能得到不同但都自称符合 PRD 的实现。

**建议补充：**

- 定义轮次或时间单位、事件排序、同一事件的唯一标识、行为触发频率、规则与行为执行先后。
- 定义多个动作写入同一属性、动作失败、事件递归触发和达到执行上限时的处理结果。
- 补齐示例中的工单状态、处理能力、排队方式、完成条件；明确“执行条件”和“前置条件”是否确实有区别，若无必要可合并。
- 为每项指标写清公式、单位、观察窗口、统计对象；尤其说明尚未完成工单是否计入等待时间，以及如何计入。
- 同步更新 Q7：若选择历史预测或更复杂仿真，应重新评审范围与依赖，而不能沿用当前固定规则版本的承诺。

**最小验收示例，供选型时采用：** 初始积压为 0，共 4 轮，每轮先新增 4 单再处理，处理能力为每轮 3 单；按 `本轮积压 = max(上轮积压 + 新增量 - 处理能力, 0)`，最后积压为 4。对比场景仅将处理能力改为 4，最后积压为 0。两次重放各自的输入应得到相同逐轮状态。此示例是建议的测试模型，不是对真实运维业务的假设确认。

### R05｜Diff 和快照缺少版本校验、整批提交及撤销冲突规则

**位置：** [FR-004，L248](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:248)、[FR-204，L334](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:334)、[FR-804，L519](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:519)。

**缺口与影响：** 用户看完 Diff 后可能又手工修改项目，再确认旧建议；整批修改可能执行到一半失败；恢复修改前快照也可能覆盖后来完成的无关编辑。这些情况在单人桌面应用里同样会发生，已有预览和快照要求尚未规定处理结果。

**建议补充：**

- ChangeSet 关联生成时的项目版本；确认时再次校验，版本不符则重新计算差异或提示处理冲突。
- 执行前完成结构与引用检查；整批修改全部生效或全部不生效。失败与取消均展示明确状态。
- 区分“撤销这一次修改”和“恢复整个项目快照”；若只能恢复全量快照，必须说明会影响哪些后续操作。
- 所有会改变正式项目的 Agent 写入均走同一入口，避免依赖“大批量”“改变含义”等难以一致判断的措辞。

**验收示例：** 生成 Diff 后手工改同一属性，旧 Diff 不得直接覆盖；执行中途失败，项目保持修改前状态；撤销前展示其影响，不能无提示地丢掉后续人工编辑。

### R06｜隐私分级还需要覆盖每次工具调用后的上下文和查询外联

**位置：** [FR-402，L383](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:383)、[FR-803，L515](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:515)、[FR-902—903，L547](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:547)、[安全与隐私，L716](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:716)。

**已有要求：** 本地模式、上下文范围、工具白名单、密钥存储和日志脱敏。

**缺口与影响：** 未明确上下文授权是否也约束后续工具返回结果、对话历史、摘要和错误信息；“只读 SPARQL”也没有独立约束网络访问。若所选引擎支持 `SERVICE`，只读查询仍可能访问远程端点。这是需要补齐的能力边界，并非认定已有数据泄露。

**建议补充：**

- 将授权绑定到项目、数据范围、用途和模型服务；每次模型请求都检查最终待发送内容，覆盖工具结果、摘要、历史和错误信息。
- 超出已授权范围时，先提供可理解的范围预览；同一范围内可复用授权，避免每一步重复弹窗。
- 明确首版查询仅访问项目内数据；若保留远程查询能力，对 `SERVICE` 等网络能力单独控制，不以只读标志代替外联策略。
- 导入内容和工具输出属于数据，不能改变工具权限或外发授权；添加相应 Agent 评估样例。
- 保留最小调用记录：目的服务、使用范围、授权结果和时间。详细 token、费用统计仍可维持 P1；记录本身也应避免重新存放敏感正文。

**验收示例：** 仅授权选中字段时，工具返回的其他列不会进入下一次模型请求；切换为完全本地后不再发送后续请求，已开始的请求按明确的取消策略处理；未授权的远程查询被阻止并解释原因。

**标准依据：** `SERVICE` 用于将部分 SPARQL 查询交给远程端点执行，因此只读与能否联网是两个独立维度。[W3C SPARQL 1.1 Federated Query](https://www.w3.org/TR/sparql11-federated-query/)

### R07｜端到端验收证明“能点完”，还不足以证明“结果对”

**位置：** [Agent 评估，L762](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:762)、[端到端验收，L776](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:776)、[后续交付物，L884](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:884)。

**已有要求：** 端到端步骤、Agent 评估主题、兼容性与恢复检查；后续计划编写案例数据和测试方案。

**缺口与影响：** 尚未承诺固定数据、正确输出和失败判定。系统即使漏查一条高危告警、错误推导设备风险，仍可能满足“执行查询”“看到一条依据”“看到场景差异”的表面验收条件。

**建议补充：** PRD 先规定每条关键能力问题必须有可核对的答案，再由案例脚本和测试方案落实数据文件。至少为各模块保存下列验收基线：

| 模块 | 验收基线应包含 |
|---|---|
| 映射 | 固定输入、实体身份、预期事实集合、重复与错误行的处理结果 |
| 查询 | 能力问题、对应查询、完整预期结果；包含空结果和语法正确但语义错误的样例 |
| SHACL | 预期违规对象、违反的约束、修复后结果 |
| 推理 | 应推导和不应推导的事实、有效依据链、输入撤回后的结果 |
| 行为 | 应触发与不应触发事件、唯一动作效果、重复事件和冲突处理 |
| 沙盘 | 固定场景、逐轮关键状态、指标计算和重放结果 |
| Agent | 工具失败、越界数据、过期 Diff、无依据问题、正确说明能力限制 |
| 项目恢复 | 异常退出、取消、重开后的一致性，以及能明确恢复到哪一个已提交状态 |

“可信回答失败数为零”适合作为质量目标；发布门槛应写为“在指定、版本化的评估集上零次伪造结果，所有失败可定位”，不能以有限测试推导无限场景保证。

**验收示例：** 一条查询能够执行但漏掉预期设备时判失败；工具报错后 Agent 声称检查通过时判失败；只比较推导条数相同而不比较具体事实，不算验证通过。

## 三、三项重要完善建议

### R08｜补一张能力矩阵，避免“业务语言”掩盖语义差别

**位置：** [FR-201，L320](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:320)、[FR-203，L328](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:328)、[FR-501，L410](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:410)、[Q6，L876](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:876)。

Q6 已经提出选择推理能力的问题；新增建议是让最终选择可被用户理解和测试：

- 区分“设备可以发生告警”的结构定义，与“设备 A 发生告警 X”的具体事实，明确 FR-201 分别生成什么。
- 解释 OWL 的缺失事实不自动等于假，以及定义域/值域的推导含义；必填等业务数据约束应明确采用何种 SHACL 约束表达。
- 列出每项构造是否可导入、可编辑、可验证、可推理、可解释、可无损导出。解析成功不能直接等同于这些能力全部具备。
- 遇到合法但不支持的内容，要选择“拒绝并说明”或“保留并明确编辑限制”；禁止静默丢弃后再导出。
- 明确推理解释覆盖范围，避免实现只对自定义规则提供依据，而交互让用户以为所有结论均可解释。

**验收示例：** 一份包含不支持构造的合法 Turtle 文件不能被静默删减；没有记录某设备的告警，不自动展示成“该设备不存在告警”；表单创建的类间结构与实例事实能通过实际 RDF 核对。

上述标准语义可核对 [W3C OWL 2 Primer，第 2、4.6 节](https://www.w3.org/TR/owl2-primer/)。本报告指出的是教学与产品行为尚未明确，未认定现有文字已经采用错误实现。

### R09｜明确离线教学入口，并加入最小学习效果验证

**位置：** [FR-101—104，L276](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:276)、[课程内容，L681](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:681)、[可用性验收，L754](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:754)、[离线闭环，L780](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:780)。

**缺口：** 课程提示内容已经列入需求，但分级提示被描述成 Agent 能力，尚未说明无模型时“给我提示”“解释错误”等按钮的行为。完成点击流程也不直接等于理解本体方法。

**建议：** 内置案例提供离线提示、演示和确定性错误解释；模型启用后再增强个性化讲解。保留独立完成案例的可用性指标，并增加少量迁移任务，例如换一组数据后独立修复约束错误、解释事实与推导结果区别。区分操作完成、使用完整示范完成和独立迁移成功，便于判断学习效果。

这不是要求首版建设考试或课程管理平台，而是让核心“学习”价值有最小验证。

### R10｜项目包可迁移与任务可恢复，需要更具体的行为约定

**位置：** [FR-1000，L563](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:563)、[反馈与恢复，L627](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:627)、[非功能需求，L702](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:702)、[迁移验收，L811](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:811)。

**缺口：** 项目包清单没有明确事实数据、原始文件、推导结果和完整运行输入是否包含；“核心内容完整”与“可在另一台设备重放”是不同承诺。耗时操作也未明确哪些必须可取消、超时后如何收尾，异常退出目前只被要求“尽量”可恢复。

**建议：**

- 给出项目包清单：必须携带、用户可选携带、不得携带，以及缺少依赖时的提示和重新关联操作。导出前显示包含的数据范围。
- 如果承诺重放，应保存足够的输入、配置及执行语义版本；若仅导出模板，应明确不能重放旧结果。
- 定义文件格式版本和不兼容版本的处理，不让升级或导入静默改坏项目。
- 对映射、推理、查询、沙盘明确排队、运行、取消、超时、失败和完成状态，设置可测试的执行上限。
- 精确规定已提交内容的恢复保证，以及未完成批次的回滚行为；增加异常退出和存储失败验收。

容量和设备指标已经列为 Q5 与 10.2 的待确认项，不重复算作新发现。但即便数据规模尚未确定，取消和失败后的数据状态仍可以先规定。

## 四、MVP 范围应如何收窄

全文 54 条 FR 中，52 条标记为 P0，2 条为 P1。这个比例本身不能证明开发工作量过大；实际问题是“三档界面＋两种 Agent 模式＋多种编辑/查询入口＋六模块”的首版支持深度还不清楚，难以估算与验证。

在沿用当前“学习优先”假设时，建议保留六模块闭环，通过限制每个模块的深度收窄首版：

| 维度 | 建议的首版边界 | 需要同步修改的内容 |
|---|---|---|
| 核心场景 | 一个设备运维案例贯穿六模块；企业 POC 用于验证迁移能力 | 指标、课程、案例和里程碑 |
| 首发平台 | 在 Q2 中选定一个先验证，第二个平台另估成本 | 安装、升级、密钥存储与兼容性验收 |
| 数据映射 | 先固定一种重跑策略；Excel 明确文件类型、工作表与值转换范围 | FR-300—304，不以“支持 Excel”概括所有情况 |
| 推理与约束 | 一个已验证的能力组合、有限模板、可追溯的规则范围 | 范围表、FR-500—504、兼容性矩阵 |
| 行为与沙盘 | 一种固定轮次模型、有限内部动作、少量业务指标 | FR-600—705、Q7 和固定预期结果 |
| 界面模式 | 共用编辑器与数据模型，先约定三档模式披露差异 | FR-005、8.4；是否延期某档需产品确认 |
| 模型与报告 | 一个明确支持的模型协议、一个首选报告格式 | FR-900、FR-1001、Q9—Q10 |

这些是待评审的范围建议，不应直接当作删减已确认需求的授权。若 Q3 最终选择企业 POC 优先，应先确定该 POC 的能力问题、数据和成功标准，再重新分配学习功能与专业能力的投入。

## 六、建议下一版 PRD 直接补充的五份附件

1. **MVP 能力矩阵**：可导入、可编辑、可执行、可解释、可导出及明确不支持项。
2. **数据变化与结果失效表**：谁依赖谁、何时过期、如何重算、历史结果如何使用。
3. **行为与沙盘语义表**：时间、事件、排序、触发、冲突、终止、状态和指标公式。
4. **Agent 授权与修改表**：读取范围、外发范围、Diff 基准、提交与恢复行为。
5. **贯穿案例验收表**：每一步的固定输入、预期输出、失败路径和复现方法。

这些附件落实后，现有 PRD 才能更稳定地指导原型、开发拆解和验收；六模块方向本身无需因本次审查而推翻。
