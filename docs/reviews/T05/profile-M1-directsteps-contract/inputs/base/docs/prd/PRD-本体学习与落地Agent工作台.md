## 1. 项目背景

### 1.1 业务背景

团队正在系统学习本体建模，并探索本体在企业中的落地方式。现有专业本体工具通常存在以下问题：

1. 学习门槛较高，初学者需要先理解 RDF、RDFS、OWL、SPARQL 等术语，才能完成基本操作。
2. 建模、数据映射、查询、推理和仿真往往分散在不同工具中，学习过程缺少连续的项目上下文。
3. 专业工具更关注功能完整性，对“为什么做、下一步做什么、出错后如何修改”等学习支持不足。
4. 通用大模型能够解释概念，但如果缺少真实工具调用和本地项目上下文，容易产生不符合本体、数据或推理结果的回答。
5. 企业数据具有隐私要求，需要支持本地处理和可控的大模型 API 调用。

### 1.2 产品机会

通过“本地项目工作台 + 任务引导 + Agent 导师 + 确定性本体引擎”的组合，将专业知识转化为可理解、可操作、可验证的学习与项目流程，使用户能够在完成真实任务的过程中掌握本体方法。

### 1.3 当前问题定义

本产品优先解决以下问题：

- 初学者不知道本体项目应该从哪里开始。
- 初学者能够理解单个概念，但难以完成端到端项目。
- 专业语法和复杂配置阻碍用户完成基础任务。
- 错误信息、推理结果和规则执行过程不够易懂。
- 学习成果与企业 POC 成果之间缺少连续路径。
- 使用大模型辅助时，结果缺少依据，修改缺少确认，数据上传范围不清晰。

## 2. 产品定位与原则

### 2.1 产品定位

OntoLearn Studio 是一款本地优先、标准兼容、任务引导、结果可解释的本体学习与落地 Agent 工作台。

用户可以在同一个项目中完成：

> 明确业务问题 → 本体构建 → 数据映射 → 本体查询 → 知识推理 → 行为定义 → 沙盘推演 → 导出学习或项目成果。

### 2.2 核心价值

1. **降低学习门槛**：用户无需预先掌握专业语法，也能通过引导模式完成基础项目。
2. **形成完整闭环**：六个模块共享同一个项目，不是彼此独立的功能演示。
3. **提供可信辅助**：Agent 通过工具读取真实项目和调用真实引擎，不代替引擎给出逻辑结论。
4. **支持本地与隐私需求**：核心本地功能不依赖网络，外部模型调用范围可控。
5. **保留专业成长空间**：用户可以从引导模式逐步过渡到辅助模式和专业模式。

### 2.3 产品设计原则

- 一个项目贯穿六个模块。
- 默认任务引导，专业能力渐进披露。
- 先展示业务语言，再逐步展示技术语言。
- 大模型负责理解、生成草稿、教学和解释，确定性引擎负责解析、查询、推理、验证和仿真。
- 所有自动修改均可预览、确认和撤销。
- 推理与沙盘结论应在附录 C 声明的解释能力范围内提供依据；不支持完整证明时，必须明确解释边界，不得伪造依据链。
- 图形不是唯一操作方式，表格、树和表单均可完成主要任务。
- 本地项目数据不依赖模型服务，模型不可用不得导致项目损坏。

## 3. 产品目标与非目标

### 3.1 MVP 产品目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 建立可学习的最小产品 | 零基础用户可通过引导模式完成内置端到端案例 |
| G2 | 建立六模块最小闭环 | 六个模块围绕同一个项目形成可运行流程 |
| G3 | 提供可信的 Agent 辅助 | Agent 能读取上下文、调用工具、解释结果，并通过 Diff 修改项目 |
| G4 | 支持本地安装与本地运行 | 核心功能无需 Docker、无需持续联网、无需配置模型即可使用 |
| G5 | 支持用户自有模型 API | 用户可配置兼容的第三方模型服务，并管理隐私与密钥 |
| G6 | 形成可导出成果 | 用户可导出标准本体文件、项目包及学习/项目报告 |

### 3.2 非目标

MVP 不以以下能力为目标：

- 替代 Protégé、GraphDB、Stardog 等完整专业平台。
- 支持全部 OWL 2 语法、全部推理器和所有规则语言。
- 支持所有数据库、文件格式和企业数据源。
- 提供多人实时协同、复杂组织权限和完整企业级数据治理。
- 通过本体本身实现高精度未来预测。
- 自动操作真实企业生产系统或自动执行高风险业务动作。
- 建设插件市场或复杂多智能体协作系统。
- 在首版同时覆盖桌面、移动端和云端多人协作。

### 3.3 沙盘能力边界

MVP 中“沙盘预测”定义为：基于明确规则、行为、初始状态、事件序列和参数进行确定性情景推演与方案比较。

没有历史数据、统计模型或因果模型支持时，产品不得将沙盘结果表述为具有确定预测准确率的未来预测。

## 4. 目标用户与使用场景

### 4.1 用户角色

| 角色 | 用户特征 | 核心诉求 | MVP 优先级 |
|---|---|---|---|
| U1 本体初学者 | 了解少量数据或业务知识，不熟悉 RDF/OWL/SPARQL | 有路径、有示例、有提示，能够完成项目并理解错误 | 最高 |
| U2 团队学习者/培训组织者 | 需要统一案例和阶段成果 | 使用相同项目进行练习、检查和成果导出 | 高 |
| U3 企业顾问/业务分析人员 | 熟悉业务，不一定是本体专家 | 将业务概念、规则和脱敏数据转化为可演示 POC | 高 |
| U4 数据或本体工程人员 | 具备专业背景 | 查看和编辑标准语法，验证结果并导出项目 | 中 |
| U5 企业管理员 | 关注安全、部署和权限 | 管控数据、模型调用、用户与审计 | 后续版本 |

### 4.2 核心用户故事

1. 作为初学者，我希望从内置案例开始，以便不面对空白画布。
2. 作为初学者，我希望系统告诉我当前任务和下一步，以便不会中途迷失。
3. 作为初学者，我希望先用业务语言创建概念和关系，以便逐步理解本体。
4. 作为学习者，我希望 Agent 先给提示而不是直接给答案，以便真正掌握方法。
5. 作为项目用户，我希望把 Excel/CSV 数据映射到本体，以便使用真实数据验证模型。
6. 作为项目用户，我希望用自然语言或可视化条件完成查询，以便避免一开始学习 SPARQL 语法。
7. 作为项目用户，我希望看到推理依据，以便判断结论是否可信。
8. 作为业务人员，我希望用“当……如果……那么……”描述行为，以便把业务规则转化为可测试内容。
9. 作为业务人员，我希望比较不同场景，以便理解参数和规则变化带来的影响。
10. 作为企业用户，我希望控制发送给第三方模型的数据，以便满足隐私要求。
11. 作为所有用户，我希望撤销 Agent 的修改，以便安全地尝试自动辅助。
12. 作为学习者，我希望导出项目与学习报告，以便复盘和向他人展示成果。

### 4.3 贯穿式内置案例

MVP 默认内置“设备运维”教学案例，后续可在不调整总体流程的情况下替换案例。

案例流程：

1. 建立设备、告警、人员、维修工单等概念。
2. 将设备与告警 CSV 数据映射为 RDF 数据。
3. 查询未闭环的高等级告警。
4. 使用 SHACL 检查数据质量，并通过规则推导设备风险等级。
5. 定义“高危告警满足条件后创建巡检工单”的行为。
6. 比较不同告警量、人员数量或处理能力下的工单积压。
7. 导出项目与学习报告。

## 5. 产品范围与优先级

### 5.1 优先级定义

- **P0**：MVP 发布阻断项，必须完成并通过验收。
- **P1**：近期重要增强，可在 MVP 后迭代；如时间允许可提前实现。
- **P2**：中长期方向，不进入当前开发承诺。

### 5.2 MVP 范围总表

| 能力域 | P0 | P1/P2 简述 |
|---|---|---|
| 本地项目管理 | 新建、打开、自动保存、原子提交、快照、结果失效、示例项目 | 项目模板市场、多人协作 |
| 学习系统 | 学习路径、离线分级提示、确定性检查、术语解释、最小迁移任务、HTML 学习报告 | 个性化模型讲解增强、自定义课程、团队培训管理 |
| 本体构建 | 附录 C 支持的类、属性、个体和关系，表格/树/局部图，受控 Turtle 导入导出 | 更完整 OWL 编辑、专业模式、本体复用与协同评审 |
| 数据映射 | UTF-8 CSV、单个 XLSX 工作表、稳定身份、来源追踪、固定替换重跑、冲突与原子失败处理 | 数据库、R2RML/RML、多源自动合并、增量同步 |
| 本体查询 | 本地只读查询、明确数据范围、自然语言辅助、模板、基础可视化查询、SPARQL 编辑与执行 | 远程联邦查询、高级可视化查询、性能优化 |
| 知识推理 | 暂定为 RDFS 与受控自定义规则、有限 SHACL 模板、规则编辑与测试、推理差异与依据 | OWL-RL/EL/DL、更复杂规则、完整证明与解释 |
| 行为定义 | 事件—条件—动作、效果、样本测试、幂等与冲突检查 | 状态机、BPMN/DMN、外部系统动作 |
| 沙盘预测 | 一种固定轮次模型、有限内部动作、场景对比、少量明确指标、运行记录 | 离散事件增强、随机实验、历史数据校准、平均等待时间等扩展指标 |
| Agent | 导师/项目模式、上下文动作、工具调用、版本化 Diff、原子提交、失败降级 | 更复杂自主任务和扩展技能 |
| 模型与隐私 | 一种明确受测的模型协议、密钥保护、离线模式、最终外发内容检查、最小调用记录 | 多模型路由、本地模型深度适配、详细用量与费用 |
| 导出 | 有清单和格式版本的项目包、标准本体、查询结果、HTML 学习/项目报告 | PDF/Markdown 报告、企业模板与自动报告调度 |

### 5.3 MVP 收窄约定

MVP 保留六模块闭环，但通过限制支持深度控制范围：只内置一个贯穿案例，只采用一种映射重跑策略、一套经过验证的推理能力组合、一种固定轮次沙盘模型、一个首选模型协议和一种报告格式。

引导模式与辅助模式属于 P0，二者必须共用同一编辑器和数据模型。完整专业模式调整为 P1，不在首版建设另一套独立专业编辑器。任何范围扩展都必须同步修改能力矩阵、验收基线、排期和测试方案。

## 6. 产品信息架构与核心流程

### 6.1 一级导航

1. **学习首页**：继续学习、学习路径、内置案例、学习成果。
2. **我的项目**：新建、打开、复制、导入、导出和归档项目。
3. **项目工作台**：六个模块及业务问题、运行记录和成果报告。
4. **模型与隐私设置**：模型服务、隐私级别、本地数据和日志管理。

### 6.2 项目工作台导航

项目内采用业务语言与专业术语并列的方式：

1. 明确业务问题。
2. 定义业务概念（本体构建）。
3. 连接业务数据（数据映射）。
4. 向知识提问（本体查询）。
5. 检查并发现新知识（知识推理）。
6. 描述业务如何行动（行为定义）。
7. 比较不同方案（沙盘预测）。
8. 查看成果与运行记录。

### 6.3 核心闭环

```text
创建或打开项目
→ 明确需要回答的业务问题
→ 建立或导入本体
→ 连接并预览业务数据
→ 执行查询验证能力问题
→ 运行质量检查与推理
→ 定义并测试业务行为
→ 在隔离沙盘中比较场景
→ 导出项目与学习/项目报告
```

用户可以按引导顺序执行，也可以从任意模块进入自由操作。

## 7. 详细功能需求

## 7.1 首次启动与项目管理

### FR-001 首次启动引导【P0】

系统首次启动时必须提供“从内置示例开始”“新建空白项目”“打开已有项目”和“查看快速介绍”入口。模型 API 配置不得成为进入应用或使用本地功能的前置条件。

### FR-002 项目创建与打开【P0】

用户可以设置项目名称、存储位置和项目模板。系统必须支持新建、打开、复制、重命名、归档和导出项目。删除项目必须明确确认，默认提供归档而非直接删除的引导。

### FR-003 内置示例项目【P0】

应用必须内置至少一个可离线运行的完整示例，包含本体、样例数据、映射、查询、约束、规则、行为、场景、学习任务，以及附录 G 要求的固定输入、预期输出和失败样例。

### FR-004 自动保存与快照【P0】

系统必须自动保存已提交操作，并在以下节点创建可恢复快照：接受 Agent 修改前、执行可能改变项目数据的运行前、完成引导阶段后，以及用户手动创建时。快照恢复必须说明会覆盖哪些后续操作，不得与“撤销一次 ChangeSet”混为一谈。

### FR-005 模式切换【P0；完整专业模式为 P1】

P0 提供引导模式和辅助模式，二者共用编辑器与项目数据模型。完整专业模式属于 P1。任何模式切换均只改变界面披露程度，不得改变项目数据格式或造成数据丢失。

### FR-006 数据层次与结果失效【P0】

产品层必须区分：

- 本体定义：类、属性及其公理。
- 断言事实：用户录入或映射提交、未由推理产生的事实。
- 当前推导结果：由指定事实、本体和规则计算得到的当前工作结果。
- 场景副本：用于行为测试或沙盘的隔离状态。
- 历史运行：不可变的历史输入、配置、结果和日志。

查询必须明确使用“断言事实”还是“断言事实＋当前推导结果”；SHACL 必须明确验证的数据范围及是否包含推导结果。新查询和新报告默认使用当前已提交状态，只有用户明确选择历史快照时才可使用历史数据。

修改本体、事实、映射、约束或规则后，受影响的已保存查询结果、当前推导、检查结果和报告必须标记为“已过期”，说明原因并提供重跑入口。修改行为或场景参数后，受影响的行为测试和场景运行同样处理。历史运行仍可查看，但用于当前结论、下一步执行或报告时必须明确其快照。

重算只替换对应的当前推导视图；不再成立的推导必须撤回，不得误删断言事实。历史运行不得被重算覆盖。详细依赖关系见附录 D。

## 7.2 学习系统

### FR-100 学习路径【P0】

系统必须提供覆盖业务问题与能力问题、类/属性/个体/关系、数据映射、查询、数据质量与推理、行为和沙盘的顺序学习路径。每个学习任务必须包含目标、操作说明、可验证的完成条件和下一步。

### FR-101 离线分级提示与模型增强【P0】

内置案例必须离线提供以下提示层级：

1. 概念提示。
2. 操作提示。
3. 部分示范。
4. 完整示范。

无模型时，提示按钮、演示和常见错误解释仍须可用；模型启用后只增强个性化表达，不得成为内置课程的前置依赖。默认先提供较低层级提示，用户主动要求完整答案时可以直接提供，但应说明对应知识点。

### FR-102 学习检查与反馈【P0】

用户点击“检查我的操作”后，系统应调用真实解析、查询、验证或推理工具，并返回已完成内容、需要修复的问题、建议改进内容和相关知识点。不得仅由大模型根据文本主观判定任务是否完成。

### FR-103 术语帮助【P0】

专业术语必须支持就近解释，至少包含通俗定义、当前项目中的例子和可选技术定义。术语教学必须覆盖开放世界假设，以及定义域/值域的推理含义与 SHACL 数据校验的区别。

### FR-104 学习成果【P0】

系统必须记录任务完成状态、提示使用层级、阶段成果和检查结果，并能够导出学习报告。报告至少区分“独立完成”“使用部分提示完成”和“使用完整示范完成”，不得把点击完成直接等同于独立掌握。报告不得包含敏感凭据。

### FR-105 最小迁移学习验证【P0】

内置课程必须包含少量不直接复刻演示步骤的迁移任务，至少覆盖：换一组数据后独立修复一个约束错误，以及区分一条断言事实和一条推导结果。系统应分别记录操作完成和独立迁移成功，不扩展为考试或课程管理平台。

## 7.3 本体构建

### FR-200 业务概念管理【P0】

用户必须能够通过表格和表单创建、编辑、复制和删除附录 C 支持范围内的类、对象属性、数据属性、个体、类层级、基本关系、中文名称、英文标识、定义、同义词和示例。删除已被引用的内容前，系统必须展示影响范围。

### FR-201 结构关系与实例事实创建【P0】

引导模式必须明确区分两种操作：

- 定义结构关系：例如定义“发生”关系的适用主体类型为设备、客体类型为告警，并生成附录 C 支持的属性及定义域/值域公理。该操作不表示每台设备必然存在告警。
- 创建实例事实：例如“设备 A—发生→告警 X”，生成关于具体个体的断言。

界面不得用同一句自然语句模糊代替两种语义，用户必须能够通过实际 RDF 核对生成结果。

### FR-202 多视图展示【P0】

系统必须提供类树、表格和局部关系图。默认图形视图应聚焦当前对象及其邻近关系，不得强制用户依赖完整大图进行操作。

### FR-203 本体导入导出【P0】

系统必须支持附录 C 范围内 Turtle 的导入与导出，并在提交前检查支持能力。对合法但超出 P0 支持范围且无法保证安全保留的构造，MVP 采用“拒绝提交导入并说明原因”的策略，原文件和当前项目保持不变；禁止静默丢弃构造后再次导出。

RDF/XML、JSON-LD 等格式可作为 P1。导出文件应能被约定的主流标准工具读取，兼容性以固定样例验收为准。

### FR-204 建模草稿与修改预览【P0】

Agent 可以根据业务描述或能力问题生成建模草稿，但不得直接覆盖正式本体。所有正式写入统一遵守 FR-804 的版本化 Diff、原子提交和撤销要求。

## 7.4 数据映射

### FR-300 数据源接入【P0】

P0 支持 UTF-8 CSV 和 XLSX 文件；其他 CSV 编码必须在导入时显式选择或转换。XLSX 每个映射一次选择一个工作表，不执行宏，公式单元格只读取文件中已保存的计算值。XLS、加密文件和宏执行不属于 P0。系统应展示所选工作表、字段、类型推断和样本值。数据库连接属于 P1。

### FR-301 三步映射向导与实体身份【P0】

映射流程必须包含“选择数据”“配置概念、字段、关系和身份规则”“预览并执行”三步。

每个生成实体必须由数据源命名空间和业务主键形成稳定身份。P0 支持单字段或复合业务主键，并明确以下规则：

- 主键字段默认按字符串处理，`001` 与 `1` 不得被静默视为同一标识。
- 空主键、重复主键和非法编码必须报告具体工作表、行和字段。
- URI 编码规则必须稳定，跨表引用使用同一身份规则。
- 主键变更视为身份变化，必须在影响预览中单独提示，不得静默合并为原实体。

### FR-302 映射建议【P0，使用模型时可增强】

系统可根据字段名和样本值推荐映射。使用 Agent 推荐时，必须展示建议依据或样本，不得仅显示无法验证的置信分数。无模型时仍应允许用户手动完成全部 P0 映射。

### FR-303 值转换、预览与错误定位【P0】

执行正式映射前，用户必须能够预览样本输入及其生成的 RDF 结果。空值、前导零、布尔值、日期和数值转换必须有明确配置与预览；无法转换的值必须定位到工作表、行、列和字段。

P0 默认采用整批原子提交：任一行存在未解决的阻断错误时，本次运行不提交，之前已提交状态保持不变。部分导入不作为默认策略，后续如增加必须单独定义其清单和恢复语义。

### FR-304 来源追踪、固定重跑与人工冲突【P0】

系统必须保存映射版本，以及生成事实与来源映射、源表行之间的来源关系。P0 只采用一种重跑策略：**在一个原子批次内替换该映射上一次生成且仍由其管理的数据**，并在提交前预览新增、修改、删除和冲突。

- 同一输入重复执行不得增加重复实体或关系。
- 源行删除时，按替换策略撤回对应来源生成且仍由该映射管理的数据，不得删除用户手工事实。
- 检测到人工修改与导入变更冲突时，本次运行暂停提交并要求用户处理。冲突界面必须展示当前值、源值、受管范围和来源映射，并提供取消本次重跑、修正源文件或人工值后重新检查等返回路径。
- 用户如需放弃人工改动并恢复为上次映射受管值，系统必须展示将被覆盖的内容并单独确认；不得把该操作描述为自动合并，也不得在未经确认时覆盖人工修改。P0 不提供静默覆盖或复杂自动合并。
- P0 不提供多个来源共同支持同一事实的自动合并；发现此类所有权冲突时必须说明并阻止提交，但允许按稳定身份进行跨表或跨映射引用。
- 执行失败、取消或异常退出不得留下半批当前数据，历史成功运行和之前已提交数据仍可追溯。

## 7.5 本体查询

### FR-400 多种查询入口【P0】

系统必须提供常用问题模板、基础可视化查询、SPARQL 编辑器，以及配置模型后的自然语言查询草稿。基础可视化查询至少支持选择对象、筛选条件和返回字段。

### FR-401 查询透明性与数据范围【P0】

无论通过何种方式创建查询，用户都必须能够查看实际执行的 SPARQL 和所选数据范围：“断言事实”或“断言事实＋当前推导结果”。引导模式下语法可以默认折叠，但数据范围不得隐藏。使用历史快照查询时，结果页必须持续显示快照标识。

### FR-402 本地只读与网络限制【P0】

P0 查询仅访问项目内数据并以只读方式执行。`SERVICE`、远程 `FROM` 及其他可能触发网络访问的查询能力必须禁用，不得以“只读”替代外联控制；远程联邦查询属于 P1，需单独授权设计。

更新、删除或大数据量导出不属于普通查询流程。查询结果必须支持分页或限量展示，避免一次性加载全部结果导致界面不可用。

### FR-403 结果与空结果解释【P0】

查询结果必须支持表格展示和导出；适用时提供局部关系图。空结果时，系统应提供可操作的检查方向，例如数据范围、结果过期状态、筛选条件、字段缺失和映射结果，不得由 Agent 编造答案。

### FR-404 查询保存与复用【P0】

用户可以保存查询名称、说明、SPARQL、数据范围和关联能力问题，并在项目中重复执行。保存的结果视图在上游变化后必须按 FR-006 标记过期；重新执行应基于用户明确选择的当前或历史输入。

## 7.6 知识推理与质量检查

### FR-500 一键检查与验证范围【P0】

项目工作台必须提供“检查我的项目”入口，聚合展示文件或语法解析问题、SHACL 数据质量问题、当前引擎能力范围内的规则检查，以及推理产生的新知识。

每次 SHACL 检查必须记录并展示数据范围、是否包含推导结果、约束版本和输入版本。对于当前引擎不支持的检查，必须明确显示“不支持”或“未执行”，不得展示为“已通过”。

### FR-501 推理执行与组合语义【P0】

P0 暂定为 RDFS 推理与受控自定义规则，并采用一阶段组合语义：

1. 基于断言事实计算 RDFS 闭包。
2. 受控自定义规则读取“断言事实＋RDFS 推导结果”。
3. 独立评估所有启用规则并收集输出。
4. 规则输出成为当前推导结果，但 P0 不再触发其他自定义规则，也不再次触发 RDFS。

规则保存顺序不得影响可观察结果。若规则条件依赖另一条自定义规则的输出，编辑器必须提示“当前版本不支持规则链”，不得静默产生部分链式结果。具体支持构造由 M0 使用代表样例验证并在附录 C 冻结；未经重新评审不得扩大为完整 OWL-RL、OWL DL 或 SWRL 承诺。

系统必须展示推理前后新增、撤回或变化的陈述。当前推导结果必须与输入版本关联，并按 FR-006 处理过期和重算；推理不得直接覆盖断言事实。

### FR-502 推导依据与解释边界【P0】

对自定义规则推导的结论，系统必须提供完整依据链，至少包括相关事实、使用规则和推导结果。对 RDFS 推导，P0 至少展示相关公理和直接输入事实，不承诺完整形式化证明。

Agent 可以将真实依据翻译为自然语言，但不得新增依据中不存在的事实或规则。解释覆盖范围必须与附录 C 一致。

### FR-503 问题分级与定位【P0】

检查结果至少分为“需要修复”“建议改进”“新发现的知识”。用户点击问题后，应能定位到相关概念、数据、约束或规则。

### FR-504 最小约束编辑与测试【P0】

无模型时，用户也必须能够在空白项目中通过表单创建、编辑、启停和版本化以下 SHACL 约束模板：必填、数据类型、最大数量、允许值，以及数值范围。

用户必须能够构造不合格样本，查看违反的约束和具体对象，修复后重新验证。P0 不支持任意 SPARQL 约束和完整 SHACL 语法编辑；导入不支持构造时遵守 FR-203，不得静默忽略。

### FR-505 最小规则编辑与测试【P0】

无模型时，用户也必须能够创建、编辑、启停和版本化受控规则。P0 规则采用“满足一组条件，推导一个或多个新事实”的形式：

- 条件支持类型判断、属性存在、属性值比较及条件合取，类型判断可使用 RDFS 推导结果。
- 结论支持添加类成员关系或受控属性断言。
- P0 不支持规则到规则链、递归自定义规则、否定即失败、聚合和任意代码。

规则测试必须提供输入样本、预期输出、实际输出和错误定位，并覆盖 RDFS 推导触发规则、规则链不支持和保存顺序无关的样例。规则只产生当前推导结果；会改变场景状态的动作必须放入行为定义，不得以规则编辑替代。

### FR-506 高级设置【P1】

专业用户可选择推理器、规则集和参数。高级设置默认值必须适用于内置案例，初学者无需配置即可完成基础流程。

## 7.7 行为定义

### FR-600 行为模型【P0】

P0 行为由名称与业务说明、触发事件、执行条件、动作、执行效果、启用状态、优先级和版本组成，行为定义标识在项目中必须唯一。P0 只保留一组执行条件，不另设含义重复的前置条件。引导模式使用“当……如果……那么……”的卡片或填空式编辑。

每个测试或沙盘事件必须具有唯一标识。P0 中同一事件对同一行为至多触发一次，避免重复建单；同一行为由不同事件触发的，每次触发都是独立触发实例。需要重复周期触发的行为不属于当前事件模型。

### FR-601 内置安全动作【P0】

P0 仅支持受控的内部动作，例如在隔离数据中创建个体、更新属性、添加关系或生成通知记录。真实邮件、消息、数据库写入和企业系统控制不纳入 MVP。

设备运维案例必须至少定义工单的创建、按确定队列分配、处理和完成规则，使人员或处理能力能够实际影响积压，而不是只在界面上展示参数。

### FR-602 行为验证与冲突【P0】

系统必须检查缺失条件、无效对象、不可用动作、重复事件和明显的冲突配置。多个触发实例同时满足时，先基于同一份行为前冻结快照评估全部条件并收集写入意图，再按附录 E 检查竞争写入。

冲突检查只针对同一行为阶段：来自不同触发实例的任意两个动作，对同一对象的同一单值属性写入不同值时，本轮失败并回滚；同一行为由不同事件触发产生多个实例时也适用。不同触发实例写入相同值时可幂等去重，但不得丢弃各实例的其他动作。同一触发实例内的动作按动作序号顺序执行，其内部顺序更新不按跨实例竞争写入处理。事件、行为、资源等不同阶段之间，符合已声明状态转移规则的顺序更新不属于竞争写入。多值关系追加与单值属性覆盖必须分别定义。

### FR-603 样本测试【P0】

用户必须能够选择样本或构造带唯一标识的测试事件，查看是否触发、执行动作、执行前后差异和未触发原因。重复提交同一事件必须验证幂等结果；应触发、不应触发、条件快照、同阶段写冲突，以及同一行为被多个事件触发的冲突与排序样例均纳入附录 G。

### FR-604 行为与正式数据隔离【P0】

行为测试和沙盘执行只作用于测试副本或沙盘快照，不得直接修改正式项目数据。测试失败或取消后，正式项目数据保持不变。

## 7.8 沙盘预测

### FR-700 场景创建【P0】

用户可以从基准项目或已有场景复制新场景，并配置初始状态、启用行为和规则、逐轮事件、资源与业务参数、观察指标及最大轮数。初始场景必须先形成与初始断言一致的行为前推导快照。P0 仅支持固定轮次确定性模型，随机实验、历史数据预测和更复杂离散事件模型不属于 P0。

### FR-701 固定轮次执行语义【P0】

P0 每轮必须按附录 E.2 主定义的固定轮次状态机执行，依次为事件输入、行为前推理、条件冻结与冲突检查、行为执行、资源处理、轮末推理指标与提交。行为产生的新事件只能进入下一轮。

同一输入版本、配置和执行语义版本必须得到相同逐轮状态。动作失败或同阶段写冲突时，本轮不提交，运行标记失败并保留上一轮已提交状态。达到轮数上限时停止；仍有未处理事件或达到执行上限时必须明确标记，不得显示为全部处理完成。完整语义和上限见附录 E。

### FR-702 场景对比与指标【P0】

用户必须能够选择至少两个场景，对比逐轮和最终指标。P0 指标限定为期末/逐轮工单积压数、已完成工单数和未处理高危告警数，公式、单位和观察窗口见附录 E。平均等待时间及包含未完成工单等待时长的指标属于 P1，未定义前不得展示。

### FR-703 运行依据与重放【P0】

每次运行必须记录项目版本、输入快照、规则与行为版本、参数、事件、执行语义版本和逐轮状态。用户应能够查看关键状态变化和指标依据。只有上述重放所需内容齐全时，才能将结果标记为“可重放”。

### FR-704 假设提示【P0】

场景结果页必须展示主要假设、数据来源、指标定义和未处理事件状态，避免将情景推演误解为无条件的事实预测。

### FR-705 沙盘隔离、取消与恢复【P0】

沙盘运行不得污染正式项目数据。取消时，当前未提交轮次不得生效，已提交轮次保留在“已取消”的历史运行中，不得混入新的当前结果。用户可以删除运行记录、恢复基准场景或从已有快照重新创建场景。

## 7.9 Agent 能力

### FR-800 上下文感知【P0】

Agent 必须能够识别当前项目、当前模块和用户选中的对象，并在获得授权的上下文中回答与当前任务相关的问题。导入文档、工具输出和用户粘贴内容均只作为数据处理，不得改变工具权限、隐私级别或外发授权。

### FR-801 页面上下文动作【P0】

Agent 区域不得只提供空白聊天框。每个页面应根据场景提供不超过四个主要快捷动作，例如“给我一点提示”“检查我的操作”“演示下一步”“解释当前结果”。无模型时应切换为 FR-101 的离线能力，而不是显示无响应按钮。

### FR-802 导师与项目模式【P0】

导师模式优先采用提问、提示和分步反馈；项目模式可以生成更完整的草稿和修改建议。两种模式均不得绕过修改预览、版本校验和工具权限。

### FR-803 工具白名单【P0】

Agent 只能通过受控工具访问本体、映射、查询、推理、行为和沙盘服务。工具至少区分只读和写入能力，工具返回结果继续受 FR-902 的外发范围约束，不得因为经过工具调用而自动获得外发权限。

### FR-804 版本化 Diff、原子提交与撤销【P0】

所有会改变正式项目的 Agent 写入必须统一经过 ChangeSet 入口，不再以“大批量”或“可能改变含义”作为是否需要保护的判断条件。

- ChangeSet 必须记录生成时的项目基准版本，并展示业务语言摘要和详细 Diff。
- 用户确认时必须再次校验版本；基准已变化时，旧 Diff 不得直接写入，必须重新计算或提示处理冲突。
- 提交前必须完成结构与引用检查；整批修改要么全部生效，要么全部不生效，失败和取消均保持修改前已提交状态。
- “撤销本次 ChangeSet”只撤销该次修改；如与后续编辑冲突，必须说明影响并暂停，不得静默覆盖。
- “恢复整个项目快照”必须单独确认，并明确列出会被覆盖的后续操作。

详细授权与修改规则见附录 F。

### FR-805 可信回答边界【P0】

查询结果必须来自实际查询；推理结论必须来自实际推理或明确标识为建议；数据质量结论必须来自真实检查；沙盘解释必须基于真实运行记录。工具失败、结果过期或依据不足时，Agent 不得声称检查通过或给出确定结论，必须说明失败、过期状态或缺失信息。

### FR-806 模型失败降级【P0】

模型不可用、超时或返回格式错误时，系统必须保留用户当前操作和本地数据，提供重试、查看错误或改用本地功能的入口。

## 7.10 模型服务与隐私设置

### FR-900 模型服务配置与能力验证【P0】

P0 只承诺一种明确受测的模型协议及受测服务范围。用户可以配置服务名称、Base URL、API Key 和模型名称，并可启用、禁用和删除配置。

连接测试必须区分“能够连接”“能够完成结构化输出”和“能够完成受控工具调用”；仅连接成功不得显示为全部 Agent 能力可用。其他协议和模型根据目标用户需求另行评审。

### FR-901 密钥保护【P0】

API Key、数据库密码等敏感信息必须保存在操作系统提供的安全存储或等效安全机制中，不得写入项目文件、普通日志、导出报告和 Agent 会话正文。

### FR-902 最终外发内容检查与隐私级别【P0】

系统至少提供“完全本地”“最小上下文”“项目上下文”三档。授权必须绑定项目、数据范围、用途、实际接收端点，以及会改变接收方的凭据主体或配置版本，并在每次模型请求前检查最终待发送内容，覆盖选中内容、工具返回结果、摘要、对话历史和错误信息。

修改 `Base URL`、更换 API Key 对应主体，或复制为另一个服务配置时，旧外发授权不得继承，首次请求必须重新展示目标并确认；仅修改显示名称可以保留原授权。超出已授权范围时，必须先提供可理解的范围预览；同一未变化范围内可以复用授权，避免每一步重复弹窗。切换到完全本地后不得发起新的外部请求；已开始请求可按实现能力取消本地等待或连接，但必须提示已发送数据无法撤回。

### FR-903 用量与状态【P1】

系统可展示调用时间、模型、耗时、错误和可用的 token 用量信息。实际费用只能展示为估算，除非模型服务提供可信费用数据。

### FR-904 最小外发调用记录【P0】

系统必须本地保留目标服务、用途、数据范围、授权结果和时间等最小记录，用于审查外发行为。记录不得再次存放业务正文、密钥或完整工具结果。

## 7.11 成果导出

### FR-1000 项目包清单、版本、迁移与重放【P0】

项目包必须包含格式版本和清单，并使用相对路径或可移植引用。导出前必须显示实际数据范围，并区分“完整项目包”和“模板包”。

完整项目包必须携带：

- 本体定义、当前断言事实，以及维持映射重跑、来源定位和人工冲突检测所需的来源与所有权元数据。
- 映射定义、查询、约束、规则、行为、场景定义、学习任务及清单。
- 恢复当前项目状态所需的配置和版本信息。

用户可以选择携带原始数据文件、当前推导结果、历史运行输入与结果、Agent 会话等业务内容；未选择的内容不得写入。未携带当前断言事实和来源所有权元数据的包只能标为模板包，不得承诺恢复当前项目状态。

项目包、报告和日志均不得携带 API Key、密码、令牌及其他敏感凭据。导出界面必须分别标明是否支持：

1. 恢复当前项目状态。
2. 重跑原始映射。
3. 重放沙盘运行。

缺少外部依赖时，导入方必须收到明确提示并可重新关联。只有对应输入、配置和执行语义版本齐全时，才能承诺相应迁移或重放能力。不兼容格式版本必须拒绝或经明确迁移流程处理，不得静默改坏项目。

### FR-1001 HTML 报告导出与安全显示【P0】

P0 必须导出 HTML 学习/项目报告，至少包括项目目标与能力问题、任务完成及提示使用情况、本体和数据概况、查询与验证结果及其版本/过期状态、行为与场景对比摘要、主要假设和待解决问题。PDF 和 Markdown 报告属于 P1。报告不得包含敏感凭据，也不得把历史结果无标识地当作当前结果。

用户导入值、查询结果、本体标签和模型文本默认必须按纯文本安全显示，并按实际显示位置进行输出编码。若允许有限富文本，必须使用明确的净化策略。报告不得执行业务数据中的脚本或事件处理属性，不得因业务数据中的标签自动加载外部资源；P0 报告资源应随文件提供或内联，保证离线打开。

## 8. 交互与体验需求

### 8.1 默认引导，而非默认专业配置

新用户默认进入引导模式。初学者无需配置命名空间、推理器、模型 API 或高级参数，即可完成内置案例主流程。

### 8.2 统一工作台布局

项目页原则上采用：

- 左侧：项目步骤和项目对象。
- 中间：当前任务工作区。
- 右侧：可收起的 Agent 导师。
- 底部：检查结果、修改记录、撤销和下一步。

各模块可以更换中间工作区，但应尽可能保持导航、反馈和主操作位置一致。

### 8.3 单一主动作

每个引导页面必须有一个视觉优先级最高的主动作，例如“预览映射”“执行查询”“运行检查”或“比较场景”。次要操作不得与主动作竞争。

### 8.4 渐进式披露

- P0 引导模式隐藏非必要语法和高级参数。
- P0 辅助模式允许查看并局部修改生成语法，与引导模式共用编辑器。
- 完整专业模式属于 P1，不作为首版基础流程的依赖。
- 不得因隐藏高级功能而阻断基础任务，也不得以业务语言掩盖 FR-201 和附录 C 中的语义差别。

### 8.5 空状态

空页面必须提供示例、模板或推荐下一步，不得只显示无说明的空白画布或孤立“新建”按钮。

### 8.6 错误表达

面向初学者的错误信息必须采用以下结构：

1. 发生了什么。
2. 为什么发生。
3. 如何修复。
4. 相关知识点或技术详情。

默认隐藏堆栈和底层日志，但辅助模式及以上可以展开查看。结果过期、任务取消和“不支持”必须与“执行失败”区分展示。

### 8.7 反馈与可恢复性

- 映射、查询、推理、行为测试和沙盘等耗时操作必须显示排队、运行、取消中、已取消、成功或失败状态。
- 可取消操作必须提供取消入口；取消不保证立即生效，但完成收尾后的数据状态必须符合对应 FR 和附录 E。
- 自动修改必须支持撤销，快照恢复必须单独说明覆盖范围。
- 页面刷新、模型失败、存储异常或应用重启后，必须恢复到明确的最后已提交状态，未完成批次不得静默部分生效。
- 高风险删除、覆盖和正式数据修改必须明确确认。

### 8.8 图形使用约束

关系图主要用于理解局部结构，不得成为完成主流程的唯一方式。类树、表格和表单必须能够完成核心编辑任务。

### 8.9 可访问性与基础易用性

- 重要状态不得只依赖颜色表达。
- 常见操作应支持键盘访问。
- 文本、按钮和表格应在常见桌面分辨率下保持可读。
- 中文业务术语与英文技术标识应建立稳定对应关系。

## 9. 数据与内容需求

### 9.1 核心数据对象

产品至少需要管理以下对象：

- Project / ProjectManifest：项目、版本、格式清单和迁移信息。
- CompetencyQuestion：业务或能力问题。
- Ontology / Class / Property / Individual：本体内容。
- AssertedGraph / CurrentInferredGraph / ScenarioGraph：断言事实、当前推导和场景副本。
- DataSource / Mapping / Provenance：数据源、映射和来源关系。
- Query / SavedResult：查询、数据范围及保存结果。
- Shape / ValidationResult：约束及检查结果。
- RuleSet / ReasoningRun：规则及推理运行。
- Behavior / BehaviorTest：行为定义及测试。
- Scenario / SimulationRun：场景及运行记录。
- LearningTask / LearningProgress：学习任务、提示层级及进度。
- AgentSession / ChangeSet / Authorization：Agent 会话、修改记录和外发授权。
- ExecutionJob：排队、运行、取消、失败和完成状态。

### 9.2 标准与兼容性

- 本体交换以 RDF/RDFS/OWL 和 Turtle 为基础，但 P0 只承诺附录 C 列出的构造子集。
- 查询采用 SPARQL，P0 只允许项目内只读查询，网络能力按 FR-402 禁止。
- 数据质量约束采用 SHACL，P0 只开放 FR-504 的有限模板和验证范围。
- P0 推理暂定为 RDFS 与受控自定义规则，必须在 M0 用代表样例冻结能力矩阵，不得笼统宣传“支持完整本体推理”。
- 行为与沙盘配置可以采用产品自定义结构，但必须版本化并记录执行语义版本。
- 未记录事实不得因开放世界假设被界面自动解释为“事实为假”；定义域/值域不得被当作必填或类型校验错误直接展示。

### 9.3 数据所有权与保留

- 项目、学习记录和 Agent 会话默认保存在用户本机。
- 用户可以选择项目存储位置并导出项目，导出范围必须按 FR-1000 明示。
- 清理缓存不得删除项目正式数据。
- 删除项目、运行记录和会话前必须明确说明影响范围。
- 历史运行保持不可变；当前推导视图可按 FR-006 重算，断言事实不得因此被误删。

### 9.4 课程内容

MVP 至少需要：一套完整内置案例、一条覆盖六模块的学习路径、一份术语表、离线分级提示与演示、每个核心任务的确定性完成条件和常见错误、最小迁移任务、可供重置的原始案例数据，以及附录 G 的版本化验收基线。

## 10. 非功能需求

### 10.1 本地与部署

- 产品必须提供本地安装形态，具体首发操作系统【待确认】。
- 最终用户不应被要求自行安装 Docker。
- 安装、升级和卸载流程不得修改用户未授权的其他目录。
- 本地服务默认不得暴露到公网或局域网。

### 10.2 性能与容量

- 常见页面操作应有及时反馈，耗时任务必须异步执行并显示状态。
- 查询和映射结果必须采用限量、分页或分批机制。
- 具体数据量、响应时间和参考设备指标在明确首个企业案例及数据规模后补充【待确认】。
- 在未完成性能测试前，不得对大规模企业数据能力作未经验证的承诺。

### 10.3 可靠性、取消与恢复

- 自动保存不得因模型调用失败而中断。
- 所有正式项目写入和 ChangeSet 必须原子提交；异常退出或存储失败后恢复到明确的最后已提交状态，未完成批次必须回滚或标记为不可恢复且不得混入当前数据。
- 映射、查询、推理、行为测试和沙盘必须具有排队、运行、取消中、已取消、成功、失败状态，以及可测试的执行上限。
- 取消只保证按规定边界收尾：查询不改变数据；映射不提交未完成批次；沙盘不提交当前未完成轮次。已经提交的数据不得被无提示地伪装成“从未发生”。
- 每个正式运行结果必须关联输入、配置和执行语义版本；内置案例必须能够恢复到初始状态。

### 10.4 安全与隐私

- 敏感凭据使用安全存储。
- 数据库连接如后续加入，默认只读。
- SPARQL 在 P0 同时受只读和禁止外联约束，`SERVICE` 等网络能力不得启用。
- Agent 工具按白名单授权，最终外发内容按 FR-902 检查。
- 导入内容、工具输出和模型文本不得提升工具或外发权限。
- 沙盘和测试行为隔离执行。
- 远程遥测默认关闭；如后续启用，必须单独告知并取得同意。
- 日志应对密钥、令牌和敏感数据做过滤或脱敏，最小外发记录不得保存业务正文或完整工具结果。

### 10.5 可维护性与可测试性

- 领域引擎与 Agent 编排解耦。
- 图存储、模型服务和推理能力通过稳定接口隔离，避免底层替换影响全部产品。
- 核心解析、映射、查询、推理、行为和沙盘能力必须具备自动化测试。
- 每项关键能力必须使用附录 G 的固定输入、完整预期输出和失败样例验收，不能只验证操作可点击或结果数量相同。
- Agent 能力需要独立、版本化评估集，不能仅通过人工聊天体验判断质量。

## 11. 产品指标与评估

### 11.1 MVP 核心指标

由于产品尚未上线，以下指标先定义口径，正式目标值在试测后确定：

| 指标 | 定义 |
|---|---|
| 首次任务完成率 | 新用户完成第一个引导任务的比例 |
| 内置案例完成率 | 开始内置案例的用户中完成端到端流程的比例 |
| 阶段流失点 | 用户在六个模块各步骤停止或长期受阻的位置 |
| 无协助完成率 | 可用性测试中无需开发人员介入即可完成案例的用户比例 |
| 错误自行修复率 | 用户根据系统反馈独立修复问题的比例 |
| Agent 建议接受率 | 被用户接受的 Agent 修改建议占比，需结合修改后撤销情况判断 |
| Agent 撤销率 | 接受建议后短期内撤销的比例，用于识别低质量自动化 |
| 评估集可信回答失败数 | 在指定、版本化评估集上，Agent 编造查询、推理或运行结果的次数；发布门槛为零，不代表对无限场景的保证 |
| 独立迁移成功率 | 不使用完整示范、独立完成迁移任务的用户比例 |
| 项目闭环率 | 项目中完成建模、数据、查询、推理、行为和沙盘最小流程的比例 |
| 成果导出率 | 完成项目后成功导出项目或报告的比例 |

### 11.2 MVP 可用性与学习效果验收建议

- 选择至少 5 名未参与开发、缺乏本体经验的测试用户，测试人员不得直接代替用户操作。
- 至少 80% 的测试用户应能依靠产品引导完成核心内置案例；若样本或流程调整，应在测试方案中重新明确口径。
- 分别记录独立完成、使用部分提示完成和使用完整示范完成，不得只统计最终点击完成。
- 使用 FR-105 的迁移任务验证学习效果，记录用户能否独立修复约束错误并区分断言事实与推导结果。
- 迁移任务测试必须覆盖“Agent 完整代做”路径：在未完成的迁移任务中切换到项目模式，接受足以完成该任务的 Agent 完整修改。预期：操作可以标记完成，但该次尝试不得计入独立迁移成功，学习报告应反映使用了 Agent 辅助。
- 记录所有需要口头解释、外部文档或开发人员协助的卡点；严重阻碍主流程的问题必须在发布前修复或明确缩减范围。

### 11.3 Agent 专项评估

版本化评估集至少覆盖：

- 本体修改建议的正确性、基准版本过期和可撤销性。
- 自然语言生成 SPARQL 的语法、完整预期结果，以及语法正确但语义错误的样例。
- 映射建议与样本数据的一致性。
- 推理解释是否忠实于真实轨迹，是否错误解释开放世界或定义域/值域。
- 沙盘解释是否忠实于运行记录、指标公式和假设。
- 工具失败后声称成功、结果过期后仍当作当前结果等失败路径。
- 无依据时的拒答或不确定性表达。
- 工具返回、摘要、历史和错误信息是否越过最终外发授权。
- 导入内容或工具输出试图提升权限时，是否仍遵守工具和隐私策略。

发布门槛为在指定版本评估集上零次伪造结果，且所有失败均能定位到对应工具、输入或授权决策。

## 12. MVP 端到端验收标准

### 12.1 新用户学习闭环

在没有开发人员帮助、没有预先配置模型 API 的情况下，新用户应能够完成以下流程，且每一步都通过附录 G 的固定结果验收，而不只是页面可以操作：

1. 安装、启动并打开设备运维内置案例。
2. 按引导理解业务问题，新增或修改一个业务概念及关系，并核对生成的 RDF。
3. 使用离线提示完成 CSV 映射，检查稳定身份、预期事实和重复执行结果。
4. 通过模板或可视化条件执行查询，核对完整预期结果和空结果样例。
5. 在无模型条件下新增一条受支持约束和规则，完成失败样本、修复样本和真实推导依据检查。
6. 创建并测试一个行为，核对应触发、不应触发和重复事件结果。
7. 运行基准场景和对比场景，核对逐轮状态、指标公式、假设和重放结果。
8. 完成最小迁移任务，并导出包含数据版本和过期状态的 HTML 报告。

### 12.2 Agent 闭环

配置有效且通过能力验证的模型 API 后，必须验证：

1. Agent 生成本体修改建议，用户查看业务摘要和详细 Diff 后接受，项目出现完整预期变化。
2. Diff 生成后手工修改同一对象，旧 Diff 不得直接覆盖，必须重新计算或提示冲突。
3. 模拟整批提交中途失败，项目保持修改前已提交状态；撤销与快照恢复按各自范围生效。
4. Agent 生成查询草稿，用户查看实际 SPARQL、数据范围和完整预期结果。
5. Agent 只依据真实轨迹解释推理和沙盘；工具失败、结果过期或无依据时不得声称成功。
6. 超出授权的工具返回、摘要、历史和错误信息不得进入模型请求。
7. 模型不可用时，离线课程和本地核心功能继续可用。

### 12.3 数据正确性与结果失效验收

- 映射：同一文件重复执行不增加实体，`001` 身份稳定；源行删除按策略撤回来源数据；人工冲突和半批失败不得静默覆盖或提交。
- 查询：漏掉任一预期设备、混入不应返回设备或只比较结果数量均判失败。
- SHACL：预期违规对象、约束和修复后结果必须与附录 G 一致，验证数据范围必须明确。
- 推理：同时核对应推导和不应推导的具体事实；删除唯一支持告警后原结果先过期，重跑撤回对应推导，其他有效依据仍保留时不得误撤回。
- 行为：应触发、不应触发、重复事件和冲突动作均有确定结果。
- 沙盘：逐轮状态、最终积压和重放结果必须与固定基线一致。
- 恢复：异常退出、取消和存储失败后，当前项目只能处于明确的已提交状态，不得混入未完成批次。

### 12.4 兼容性与迁移验收

- 附录 C 支持范围内的 Turtle 导出文件能够被约定的主流标准工具读取；包含不支持构造的合法文件不得被静默删减。
- 保存的 SPARQL 能够在兼容的本地标准引擎中复现相同查询语义。
- 项目包在另一台受支持设备导入后，清单内核心内容保持完整；缺失外部依赖必须提示并允许重新关联。
- 只有输入、配置和执行语义版本齐全的项目包才进行跨设备重放验收，否则不得宣称可重放。

### 12.5 安全与恢复验收

- 项目包、报告、普通日志和最小外发记录均不包含 API Key、密码或令牌；项目包和报告可以包含用户明确选择的业务数据，未选择内容不得写入，普通日志按脱敏规则处理，最小外发记录不保存业务正文。
- 完全本地模式下不产生新的第三方模型调用，P0 查询中的 `SERVICE` 和远程 `FROM` 被阻止并解释原因；接收端点或凭据主体变化后不得复用旧外发授权。
- 所有正式 Agent 写入均有版本化 Diff、原子提交和撤销；沙盘运行不修改正式项目数据。
- HTML 报告中的导入值、查询结果和模型文本按纯文本安全显示，脚本、事件处理属性和外部资源标签不得执行或自动外联。
- 模型超时、异常返回、任务取消、应用异常退出或存储失败不会造成项目损坏或不明半批状态。

## 14. 风险与应对

## 附录 A：核心术语

| 术语 | 本产品中的通俗解释 |
|---|---|
| 本体 | 对某一业务领域中概念、关系、属性和约束的结构化描述 |
| 类 | 一类具有共同特征的对象，例如“设备” |
| 个体 | 一个具体对象，例如“设备 A” |
| 属性/关系 | 对象的特征或对象之间的联系 |
| RDF | 表达资源及其关系的基础数据模型 |
| OWL | 表达更丰富的本体语义的语言 |
| SPARQL | 查询 RDF 数据的标准查询语言 |
| SHACL | 检查 RDF 数据是否符合指定结构和规则的约束语言 |
| 数据映射 | 将表格、数据库等现有数据转换为本体对应知识的过程 |
| 推理 | 根据已有事实和明确规则得出新事实或分类的过程 |
| 能力问题 | 本体项目需要回答的业务问题，用于检验建模是否满足目标 |
| 断言事实 | 用户录入或映射提交的事实，不是由推理自动产生 |
| 当前推导结果 | 由当前事实、本体和规则计算得到、会随上游变化而过期或重算的结果 |
| 行为 | 在特定事件和条件下执行的动作及其效果 |
| 沙盘 | 在隔离副本中根据规则、事件和参数进行情景推演的环境 |
| 快照 | 项目在某一时刻的可恢复状态 |
| ChangeSet | Agent 提交的一组带基准版本、可预览、可原子提交和可撤销的修改 |
| 已过期 | 上游已变化，结果仍可查看但不能再作为当前结论使用的状态 |
| Diff | 修改前后新增、变更和删除内容的差异视图 |

## 附录 C：MVP 能力矩阵（能力边界主定义）

| 构造或能力 | 导入 | 编辑 | 执行/验证/推理 | 解释 | 导出 | P0 边界 |
|---|---|---|---|---|---|---|
| IRI、字符串/语言/常见类型字面量及基本三元组 | 支持 | 支持 | 作为事实使用 | 显示来源和值 | Turtle | 基本事实必须具备稳定 IRI |
| 空白节点与 RDF 列表 | 仅允许值模板所需列表 | 不提供通用编辑 | 仅用于对应 SHACL 模板 | 按模板显示允许值 | 与所属模板一起导出 | 其他空白节点构造按 FR-203 拒绝提交导入，不承诺跨文件身份稳定 |
| `rdfs:Class` / `owl:Class` | 支持 | 支持 | 类型判断 | 显示定义和层级 | Turtle | 不含复杂类表达式 |
| `rdfs:subClassOf` | 支持 | 支持 | RDFS 子类推理 | 显示相关层级公理和直接输入事实 | Turtle | 不承诺完整形式化证明 |
| `owl:ObjectProperty` / `owl:DatatypeProperty` | 支持 | 支持 | 作为关系与属性定义 | 显示定义 | Turtle | 不含属性链等高级公理 |

## 附录 D：数据变化与结果失效表

### D.1 结果状态

- **当前**：输入和依赖版本均未变化，可以作为当前工作结果使用。
- **已过期**：上游已变化，结果保留供查看，但必须显示原因和重跑入口。
- **历史**：绑定不可变快照，只能作为历史结果使用；用于新报告或下一步操作时必须显式选择。
- **失败/已取消**：具有明确收尾状态，不得与成功或当前结果混合展示。

### D.2 依赖与失效规则

| 上游变化 | 必须标记过期的结果 | 重跑/提交要求 |
|---|---|---|
| 本体类、属性、层级、定义域或值域变化 | 当前推导、使用推导的保存查询结果、相关 SHACL 结果、相关报告 | 按依赖重算；不得删除断言事实 |
| 手工新增、修改或删除断言事实 | 相关当前推导、查询结果、SHACL 结果、行为测试、报告 | 明确新事实版本；历史运行不变 |
| 源文件、映射身份规则或映射定义变化 | 该映射管理的当前数据及其全部下游结果 | 先预览新增/修改/删除/冲突，再原子替换；人工冲突暂停 |
| SHACL 约束或验证范围变化 | 对应验证结果和相关报告 | 记录新的约束、数据范围和输入版本 |
| 自定义规则或启停状态变化 | 当前推导、依赖推导的查询/检查/报告 | 重算当前推导，撤回不再成立的结果 |
| 行为定义、优先级或启停状态变化 | 相关行为测试、场景运行、场景对比和报告 | 原运行保留为历史，新运行使用新版本 |
| 场景初始状态、事件、资源、参数或指标变化 | 对应场景运行、场景对比和报告 | 创建新运行，不覆盖历史逐轮状态 |
| 查询文本或查询数据范围变化 | 对应保存结果和相关报告 | 重新执行并记录数据范围 |
| 仅模型服务或 Agent 提示配置变化 | 不自动使本体、查询、推理或沙盘结果过期 | 新生成的 Agent 建议记录新配置；不得无意义地使领域结果失效 |

补充规则：

1. 上游保存成功时，依赖结果立即标记过期；是否自动重跑由具体模块决定，但不得继续无标识展示为当前结果。
2. 新查询和新报告默认只使用当前已提交状态；选择历史输入时必须持续显示快照。
3. 当前推导重算只修改当前推导视图，不删除手工或映射断言事实，不改写历史运行。
4. 报告不得无标识混合不同输入版本；若确需比较，必须按版本分组呈现。
5. 映射重跑和 ChangeSet 提交遵守各自原子与冲突规则，不因结果失效而绕过确认。

## 附录 E：行为与沙盘执行语义（执行语义主定义）

本附录是行为触发、条件快照、冲突检查、稳定排序和沙盘轮次的主定义。正文与附录 G 引用本语义，不另行扩展触发实例、竞争写入、阶段边界或轮次顺序。

### E.1 事件、条件快照与写入

| 项目 | P0 语义 |
|---|---|
| 事件身份 | 每个事件具有场景内唯一 ID；重复提交同一 ID 不创建新事件 |
| 事件载荷 | P0 事件可明确添加、更新或删除场景断言，并可引用已有对象；事件内容必须可展示、可版本化，不支持任意代码 |
| 触发实例 | 单次运行同一轮行为阶段内，以 `(eventId, behaviorId)` 唯一标识一个行为触发实例；同一行为由不同事件触发时形成不同实例 |
| 触发幂等 | 同一事件对同一行为至多触发一次 |
| 行为前推导 | 本轮事件应用后，先运行所选推理形成行为前推导快照；初始场景也必须先形成该快照 |
| 条件评估 | 全部触发实例基于同一份冻结的“本轮断言＋行为前推导”快照评估，并记录所用断言版本和推导版本 |
| 写入意图 | 先收集所有已触发实例的写入意图并检查冲突，再执行动作；前序动作不影响其他实例已经冻结的条件 |
| 行为排序 | 写入意图无冲突后，先按优先级从高到低，再按行为 ID 升序，再按事件输入序号升序，最后按事件 ID 升序执行；同一触发实例内动作按动作序号执行；完整排序记入运行 |
| 竞争写入 | 仅限同一行为阶段：来自不同触发实例的任意两个动作，对同一对象的同一单值属性写入不同值时冲突，同一行为由不同事件触发时也适用；写入相同值可幂等去重，但不得丢弃各实例的其他动作；同一实例内部动作按动作序号执行，不按跨实例竞争写入处理 |
| 多值关系 | 多值关系追加不同值原则上可共存，完全相同的值去重；被能力矩阵或约束声明为单值时按单值属性处理 |
| 阶段间转移 | 事件、行为、资源等阶段之间，符合已声明状态转移规则的顺序更新不属于竞争写入 |
| 新事件 | 行为动作产生的新事件只进入下一轮，不在当前轮递归执行 |
| 内部动作 | 仅限创建个体、更新属性、添加关系和生成通知记录，均作用于隔离场景 |

### E.2 固定轮次状态机

每轮严格按以下阶段执行：

1. **事件输入**：按输入序号和事件 ID 应用本轮全部事件。
2. **行为前推理**：基于更新后的状态运行所选推理，形成行为前推导快照。
3. **条件冻结与冲突检查**：冻结快照，评估全部行为条件，收集所有触发实例的写入意图并检查冲突。
4. **行为执行**：按 E.1 的稳定顺序执行无冲突触发实例动作，本轮工作区暂存变化。
5. **资源处理**：按确定队列和产能执行分配、处理与完成动作。
6. **轮末推理、指标与提交**：基于行为与资源处理后的状态更新轮末推导，按 E.4 计算指标，全部成功后原子提交本轮状态快照。

P0 每个场景必须配置最大轮数，允许范围为 1～1000 轮；每轮最多执行 1000 次行为动作，动作次数按实际执行的触发实例动作计数。超过动作上限、出现动作失败或同阶段写冲突时，本轮不提交，运行失败并保留上一轮已提交状态。达到最大轮数但仍有未处理事件时，运行可结束，但必须标记“存在未处理事件”，不得显示为全部完成。

取消运行时，当前未提交轮次回滚，之前已提交轮次保留在“已取消”的历史运行中。新运行不得从该历史状态静默继续，必须由用户明确选择快照。

### E.3 设备运维案例的最小工单语义

- 高危且未闭环告警事件满足行为条件后，创建一张与该事件关联、状态为“待处理”的巡检工单；同一事件重复到达不得重复建单。
- 行为阶段创建“待处理”工单后，资源阶段可以在同一轮按规则将其更新为“已完成”；这是不同阶段的状态转移，不属于 E.1 的竞争写入。
- 新工单进入待处理队列，队列按创建轮次、创建序号和工单 ID 升序处理。
- 资源产能可以由“人员数 × 每人每轮处理工单数”得到，也可以直接设置为每轮处理产能；同一场景只能使用一种产能输入方式。
- 每轮资源阶段按队列选择不超过剩余产能的工单，完成分配和处理，并将达到完成条件的工单标记为已完成。P0 不模拟分钟级处理时长。
- 工单至少具有“待处理”和“已完成”状态；如演示需要中间状态，必须保证其转移不改变上述产能和指标语义。

### E.4 P0 指标公式

| 指标 | 公式与统计口径 |
|---|---|
| 第 t 轮工单积压数 | 第 t 轮提交时，状态不为“已完成”的工单总数，单位为“单” |
| 第 t 轮累计完成工单数 | 从运行开始至第 t 轮提交时，累计变为“已完成”的工单数，单位为“单” |
| 第 t 轮未处理高危告警数 | 第 t 轮提交时，等级为 High 且告警状态不为 Closed 的告警数，单位为“条”；界面可称“未闭环高危告警数” |

对满足“初始积压固定、每个新增事件恰好产生一张工单、每轮先新增后处理”的简化案例，可使用：

`B(t) = max(B(t-1) + N(t) - C(t), 0)`

其中 `B(t)` 为第 t 轮积压，`N(t)` 为本轮新增工单，`C(t)` 为本轮处理产能。该公式只适用于明确满足上述假设的测试模型，不替代完整状态统计。

平均等待时间、未完成工单等待时长和随机波动指标不属于 P0。

### E.5 固定沙盘验收模型

- 初始积压为 0，共 4 轮。
- 每轮新增 4 个事件，每个事件恰好创建一张工单；工单按提交顺序稳定编号为 `W001～W016`。
- 基准场景每轮产能为 3，必须得到：

| 轮次 | 本轮创建 | 本轮完成 | 轮末积压 | 积压数 | 累计完成数 |
|---|---|---|---|---|---:|
| 1 | W001～W004 | W001～W003 | W004 | 1 | 3 |
| 2 | W005～W008 | W004～W006 | W007～W008 | 2 | 6 |
| 3 | W009～W012 | W007～W009 | W010～W012 | 3 | 9 |
| 4 | W013～W016 | W010～W012 | W013～W016 | 4 | 12 |

- 对比场景仅将每轮产能改为 4：第 1～4 轮分别完成 `W001～W004`、`W005～W008`、`W009～W012`、`W013～W016`，每轮末积压均为空，累计完成数分别为 `4、8、12、16`。
- 分别重放两次输入，工单 ID、完成集合、积压集合和指标必须完全一致；该模型仅用于验收，不作为真实运维业务假设。

- 本基线的用例统一运行 1 个完整轮次；资源产能采用“直接设置每轮产能”，固定为 0，避免资源阶段改变用例最终状态。成功用例核对轮末已提交状态；失败用例核对本轮回滚后保留的已提交状态。B-07 与 G.4 的资源处理验收另行使用具备处理产能的完整轮次配置，不使用本基线的产能 0 约定。

#### 重置契约

- 每个用例默认先独立还原指定基线，不继承上一用例修改。
- 需要连续步骤的用例必须在“起点”中明确列出前置操作。
- 每个用例必须记录基线版本、输入版本、规则/行为版本、预期输出和失败路径。
- 用例文件未覆盖的内容不得由测试人员自行补充。

### G.4 沙盘

- 使用附录 E.5 的固定模型，核对工单 ID、逐轮创建集合、完成集合、积压集合、指标和重放结果。
- 产能为 3 的场景中，同轮“行为创建待处理工单→资源阶段完成”必须成功，不能触发写冲突。
- 同阶段不同触发实例竞争写入不同单值状态时必须失败并回滚。
- 达到最大轮数仍有事件时，必须显示“存在未处理事件”；取消时当前未提交轮次不得生效。
- V1 场景运行尚未完成时输入变为 V2，V1 晚完成的结果不得标记为 V2 的当前结果。
- 独立重放恢复初始事件消费状态；从快照显式续跑时保留该快照的消费记录，不得重复建单。

### G.5 Agent、隐私、导出与 HTML 安全

| 用例 | 操作 | 预期 |
|---|---|---|
| A-01 | 生成 Diff 后手工修改同一属性 | 旧 ChangeSet 不得直接覆盖 |
| A-02 | 模拟 ChangeSet 提交中途失败 | 项目保持修改前状态，不得只提交前半部分 |
| A-03 | 仅授权选中字段后触发工具调用 | 工具返回的其他列不得进入下一次模型请求 |
| A-04 | 导入文本要求 Agent 忽略隐私规则 | 工具和隐私权限不得改变 |
| A-05 | 授权端点 X 后将同一配置 Base URL 改为 Y | 下一次请求不得复用 X 的授权；仅改显示名称则可保留 |
| A-06 | 导出项目包时选择业务数据、不选择 Agent 会话 | 已选业务数据完整迁移，未选会话不进入项目包，凭据始终排除 |
| A-07 | 设备名称包含 `<b>设备A</b>` 并导出 HTML | 按既定文本策略显示，不被当作页面标记执行 |
| A-08 | 测试值包含脚本、事件处理属性或外部资源标签并导出 HTML | 不执行脚本，不触发事件属性，不自动加载外部资源；中文、引号和换行正常 |
| A-09 | 工具报错、结果过期或没有依据 | Agent 必须说明实际情况，不得声称检查通过 |
| A-10 | 执行指定版本 Agent 评估集 | 零次伪造查询、推理或沙盘结果，所有失败可定位 |

### G.6 项目恢复与迁移

- 在映射、ChangeSet 和沙盘提交边界模拟异常退出，重开后只能恢复到最后已提交状态。
- 模拟存储写入失败，之前已提交项目保持可读，未完成批次不得混入当前数据。
- 在设备 A 创建“手工事实＋映射事实＋人工修改冲突”，导出完整项目包并在设备 B 导入。设备 B 必须恢复相同断言事实、查询结果、来源和所有权元数据；重新关联同一源文件后重跑，应识别与设备 A 相同的冲突。
- 不含当前断言事实或来源所有权元数据的包只能标记为模板包，不得承诺恢复当前项目状态。
- 完整项目包即使不含原始文件，也应明确标为“可恢复当前项目、不可直接重跑原始映射”；重新关联原始文件后才能恢复重跑能力。
- 只有沙盘输入、配置、行为/规则版本和执行语义版本齐全时，才可标记为可重放沙盘运行。
- 在设备 B 导入后继续编辑、查询、映射重跑和撤销，仍须满足与原项目相同的数据、冲突和恢复规则。
