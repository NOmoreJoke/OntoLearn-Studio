## 2. 两项建议修改

### B01｜中：冲突检测与排序应明确采用“行为触发实例”

**位置：** [FR-600，L452](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:452)、[FR-602，L462](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:462)、[E.1，L1029](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1029)、[排序与冲突，L1033](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1033)。

**已有保护：** 同一事件对同一行为至多触发一次；同一行为阶段的竞争写入需要检查；跨阶段合法状态迁移已经允许。这些规则无需推翻。

**剩余空隙：** 幂等规则实际上以“事件×行为”为单位，但冲突文字仍写“多个行为”，排序只列优先级和行为 ID。同一个行为定义在同轮被两个不同事件触发时，会产生两个执行实例，其行为 ID 完全相同。

**最小反例：**

- 事先存在工单 W，状态为单值属性。
- 同轮两个命令事件 E1、E2 都匹配行为 B；事件仅提供目标 W 和期望状态，不直接修改 W。
- B(E1) 请求写入状态 S1，B(E2) 请求写入不同状态 S2。
- 两次触发都符合事件幂等要求；若实现按“不同的行为 ID”检查冲突，则可能漏掉这两个实例。既定排序键也无法区分二者。

**影响：** 开发和验收可能分别理解为冲突回滚、按事件顺序覆盖，或按其他顺序覆盖。文档的确定性总要求已经存在，这里需要明确的是应该确定地得到什么结果。

原文也可以被宽义理解为已经包括多个执行实例，因此本项属于消除实现歧义，不能表述为现有实现必然漏检。

**建议最小条款：**

> P0 以 `(eventId, behaviorId)` 标识一个行为触发实例。同一行为阶段内，来自不同触发实例的任意两个动作，对同一对象的同一单值属性写入不同值时，均应判为冲突，包括同一行为由不同事件触发的情况。检查通过后，按优先级、行为 ID、事件输入序号及事件 ID 稳定执行。一个触发实例内的动作按已定义顺序执行。

这不要求新增多组变量绑定机制或并发执行；如果首版不支持一次事件产生多个绑定实例，就维持该限制。

**建议增加三组验收：**

| 场景 | 预期 |
|---|---|
| 同一 B 被 E1/E2 触发，对 W 的同一单值属性写不同值 | 本轮失败，全部回滚 |
| 同一 B 被 E1/E2 触发，对不同工单写入 | 两个实例均执行，顺序和结果可重放 |
| 同一 B 被 E1/E2 触发，对同一属性写相同值 | 按既有幂等规则处理；不能因此把两个不同事件的其他动作一并丢弃 |

### B02｜中：附录 G 的部分用例仍需补完整起点或增强检错能力

**位置：** [G-base，L1125](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1125)、[重置契约，L1160](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1160)、[G.2，L1180](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1180)、[G.3，L1195](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1195)。

上述补充应写入用例本身或其明确引用的专用基线，符合 L1165“测试人员不得自行补充”的要求。无需为了这些测试对象扩展真实产品功能。

**B-04 还存在一处不同性质的问题：检错能力不足。**

[B-risk 定义，L1147](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1147) 仅匹配“新增高危未闭环告警”，而 [B-04，L1200](/Users/kyle/Documents/工作/知爻/本体/PRD-本体学习与落地Agent工作台.md:1200) 提交的是删除 A01 的事件。删除事件本身就不匹配该触发器。

需要准确区分：B-04 已经明确检查“新推导快照不再包含风险分类”，所以它能检出推导没有更新；但它还不能独立证明行为引擎实际使用了新快照。

**可绕过当前行为结果检查的错误实现：** 推理模块正确生成新快照，快照检查通过；行为引擎却读取了旧快照。因为删除事件不匹配新增触发器，行为仍不执行，于是行为结果检查也通过。两个模块之间传错快照的问题没有被检出。

**建议将 B-04 改为有区分力的探测：**

1. 从 G-base 初始化并确认旧快照中 001 为高风险。
2. 配置测试行为 B-probe：由明确的风险探测事件触发，条件仅检查 001 是否为高风险，满足时生成通知记录。
3. 同轮先删除唯一依据 A01，再提交探测事件。
4. 正确实现必须使用新快照，因此不生成通知；若行为仍读取旧快照，则会生成通知，测试应失败。

与 B-03 的“当轮新增依据后应触发”一起，可分别验证风险新增和撤回两条路径。这个探测行为只服务于验收，不需要加入正式设备运维业务流程。
